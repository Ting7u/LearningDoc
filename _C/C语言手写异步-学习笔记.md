# C 语言手写异步模型 —— 学习笔记

> 目标：不依赖任何语言层面的 async/await 语法糖，用最基础的 C 代码（函数指针 + select + 回调），从零搭建一个最简单的事件循环模型，理解"异步"到底是怎么一回事。

---

## 一、先搞清楚概念：同步/阻塞 vs 异步/非阻塞

### 1.1 阻塞（blocking）

```c
char buf[100];
read(fd, buf, 100);   // 如果 fd 暂时没有数据，这一行会卡住
printf("读到数据了\n");
```

如果 `fd` 暂时没有数据，`read()` 这一行代码会让**这一个线程**停在这里，走不到下一行，直到数据到来。

**常见误解纠正**：这不代表 CPU 在空转。操作系统调度器会把这个"卡住"的线程标记为睡眠状态，挂起，CPU 会去执行别的可运行的线程/进程，这是操作系统本来就有的多任务调度机制，跟"异步"这个话题没有直接关系。

真正的问题在于：**这一个线程自己**，此刻没法干别的事。比如：

```c
read(fd1, buf1, 100);   // 卡在这，等 fd1 来数据
read(fd2, buf2, 100);   // fd2 就算早有数据在等，也读不到，因为代码走不到这一行
```

哪怕 `fd2` 早就有数据在等着，这个线程也没法去处理它，因为它被卡在第一行动弹不得。

### 1.2 异步要解决的真正问题

> **用少量线程（甚至一个线程），去应付大量"等待中"的任务，不让任何一个任务的等待去拖累其他任务的执行。**

对比两种方案（比如要同时处理 1000 个网络连接）：

- **方案 A（多线程）**：开 1000 个线程，每个线程阻塞等自己的连接。CPU 调度没问题，但 1000 个线程的内存开销（每个线程栈可能几百 KB~几 MB）、上下文切换开销会非常大。
- **方案 B（异步/事件循环）**：只用 1 个线程，但让这个线程**从不长时间阻塞在单个任务上**，而是不断问内核"这 1000 个 fd 里，谁现在好了？"，谁好了就处理谁。

### 1.3 非阻塞模式

```c
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);

ssize_t n = read(fd, buf, 100);
if (n < 0 && errno == EAGAIN) {
    // 没有数据，但不会卡住！立刻返回，告诉你"现在没有"
}
```

设置成非阻塞模式后，没数据时 `read()` 会**立刻返回**并告知"现在没有"，而不是傻等。

## 二、为什么需要 select / poll / epoll

### 2.1 忙轮询（busy polling）的问题

如果只有非阻塞模式，为了同时处理很多 fd，只能这样写：

```c
while (1) {
    ssize_t n1 = read(fd1, buf1, 100);
    if (n1 > 0) { /* 处理 fd1 */ }
    ssize_t n2 = read(fd2, buf2, 100);
    if (n2 > 0) { /* 处理 fd2 */ }
    // ... 一直问下去
}
```

这叫**忙轮询**：不停地问"好了没？好了没？"。这次是真的在空转——哪怕所有 fd 都没数据，这个循环也在疯狂做系统调用，白白烧 CPU。

### 2.2 select / poll / epoll 的思路

> "我（线程）把这一批 fd 一次性告诉你（内核），然后我睡觉。你帮我盯着，只要**其中任何一个**有动静，就把我叫醒，并告诉我是哪几个。"

线程该睡还是睡（不浪费 CPU），但一次不是只等 1 个 fd，而是同时等一整批。

| 调用 | 思路 | 缺点 |
|---|---|---|
| `select` | 传一个 fd 集合给内核，内核挨个检查 | fd 数量有上限（一般1024），每次要重传整个集合，内核线性扫描 |
| `poll` | 和 select 类似，无数量上限 | 依然是每次线性扫描，fd 一多就慢 |
| `epoll`（Linux专属） | 内核长期记住你关心的 fd，用回调机制通知 | 效率高得多，高性能服务器标配（Nginx/Redis） |

## 三、事件循环骨架 —— 完整代码

```c
#include <stdio.h>
#include <unistd.h>
#include <sys/select.h>

#define MAX_EVENTS 10

// 函数指针类型：处理函数长什么样
typedef void (*callback_t)(int fd);

// 一张"登记卡"：哪个 fd，出事了找谁处理
typedef struct {
    int fd;
    callback_t callback;
} event_t;

event_t events[MAX_EVENTS];
int event_count = 0;

void register_event(int fd, callback_t cb) {
    events[event_count].fd = fd;
    events[event_count].callback = cb;
    event_count++;
}

void on_stdin_ready(int fd) {
    char buf[100];
    size_t n = read(fd, buf, sizeof(buf) - 1);
    if (n > 0) {
        buf[n - 1] = '\0';  // 去掉末尾的换行符
        printf("[事件] 收到键盘输入: \"%s\"\n", buf);
    }
}

void event_loop() {
    int tick = 0;
    while (1) {
        fd_set readfds;
        FD_ZERO(&readfds);
        int max_fd = 0;

        for (int i = 0; i < event_count; i++) {
            FD_SET(events[i].fd, &readfds);
            if (events[i].fd > max_fd) max_fd = events[i].fd;
        }

        struct timeval timeout;
        timeout.tv_sec = 2;
        timeout.tv_usec = 0;

        int ready = select(max_fd + 1, &readfds, NULL, NULL, &timeout);

        if (ready == 0) {
            tick++;
            printf("[定时器] 第 %d 次 tick（2秒没有键盘输入）\n", tick);
            fflush(stdout);
            continue;
        }

        for (int i = 0; i < event_count; i++) {
            if (FD_ISSET(events[i].fd, &readfds)) {
                events[i].callback(events[i].fd);
                fflush(stdout);
            }
        }
    }
}

int main() {
    printf("=== 事件循环启动 ===\n");
    register_event(0, on_stdin_ready);
    event_loop();
    return 0;
}
```

**核心流程一句话**：注册事件（fd + 回调） → 循环里用 select 同时等一批 fd（或超时） → 谁好了就调用谁对应的回调。

## 四、逐个概念 + 内存图详解

### 4.1 函数指针

```c
typedef void (*callback_t)(int fd);
```

读法：从中间的名字开始，往外剥：
1. `callback_t` —— 这是我们起的名字
2. `(*callback_t)` —— 紧挨名字的 `*`，说明它是"一个指针"
3. `void ... (int fd)` —— 指针指向的东西是"一个函数：参数 int fd，返回 void"

合起来：**`callback_t` 是一种变量类型，这种变量存的是一个地址，这个地址指向一个函数**。

内存图：

```
代码段（编译后的机器指令）
┌─────────────────────────────┐
│ 地址 0x1000                  │
│ void on_stdin_ready(int fd)  │  ← 函数体的机器指令从这里开始
│ { ... }                       │
└─────────────────────────────┘

callback_t handler = on_stdin_ready;
函数名在这里"退化"成它的起始地址（跟数组名退化成指针是同一机制）

栈（局部变量）
┌──────────┬───────────┐
│ handler  │  0x1000   │  ← handler 变量里存的就是这个地址
└──────────┴───────────┘
```

调用 `handler(fd1)`：CPU 跳到地址 `0x1000`，把 `fd1` 当参数传过去执行。效果和直接写 `on_stdin_ready(fd1)` 一样，区别是"跳去哪"现在由一个**可以在运行时改变指向的变量**决定——这就是"回调"的本质：把一个地址存起来，以后再跳过去。

### 4.2 结构体数组赋值：`events[event_count].fd = fd;`

```c
typedef struct {
    int fd;               // 4字节
    callback_t callback;  // 8字节（64位系统指针大小）
} event_t;

event_t events[MAX_EVENTS];  // 全局数组，假设从地址 0x2000 开始，每格16字节
```

假设执行 `register_event(3, on_fd1_ready)`，此时 `event_count == 0`：

```
执行 events[event_count].fd = fd; 时，编译器做的事：
1. 算下标：event_count = 0 → 操作 events[0]
2. 算地址：0x2000 + 0×16 = 0x2000
3. 算偏移：.fd 是结构体第一个成员，偏移量0 → 最终写入地址 0x2000
4. 把参数 fd（值为3）写进地址 0x2000
```

```
地址        下标           内容
┌─────────┬──────────┬────────────────────────────┐
│ 0x2000  │events[0] │ fd=3    callback=0x1000     │ ← 两个成员都填好了
├─────────┼──────────┼────────────────────────────┤
│ 0x2010  │events[1] │ fd=???  callback=???        │
└─────────┴──────────┴────────────────────────────┘
```

`event_count` 本身是一个独立的整数变量，记录"数组里已经填了几张卡片"（C 数组本身不知道自己"实际用了多少"，必须手动记账）。填完一张卡片后 `event_count++`，下次就填到下一格。

**一句话总结**：`结构体变量.成员名 = 值`，本质就是"用下标算出一块内存的地址（基地址+偏移），把值写进那块内存"。

### 4.3 `fd_set` 与 `FD_ZERO` / `FD_SET` / `FD_ISSET`

`FD_ZERO`、`FD_SET`、`FD_ISSET` **不是函数，是宏**（编译时被文本替换，没有真正的函数调用开销）。它们操作的 `fd_set`，本质是一块内存，可以理解成一排"开关"（位图/bitmap），每一位对应一个可能的 fd 号。

```
fd_set readfds （简化理解，每个格子代表一个 fd 号是否被关心）

下标(fd号): 0  1  2  3  4  5 ...
位的值:     0  0  0  0  0  0 ...
```

- **`FD_ZERO(&readfds)`**：把整排格子清零 —— "现在我谁都不关心"
- **`FD_SET(3, &readfds)`**：把第 3 号格子拨成 1 —— "我关心 fd=3"

```
FD_SET(3, &readfds); FD_SET(5, &readfds); 之后：
下标(fd号): 0  1  2  3  4  5 ...
位的值:     0  0  0 [1] 0 [1] ...
```

- **`select()` 返回后**，内核会**原地改写**这个位图：把没就绪的位清掉，只留下真正就绪的：

```
假设只有 fd=3 就绪：
下标(fd号): 0  1  2  3  4  5 ...
位的值:     0  0  0 [1] 0  0  ...
```

- **`FD_ISSET(3, &readfds)`**：检查第 3 号格子现在是不是 1 —— 用来判断"这个 fd 刚才是不是真的就绪了"

所以事件循环里这一段：

```c
for (int i = 0; i < event_count; i++) {
    if (FD_ISSET(events[i].fd, &readfds)) {
        events[i].callback(events[i].fd);
    }
}
```

翻译成人话：**挨个问账本上登记的每个 fd，"你那个格子现在是亮的吗？"——亮的（真正就绪的）就调用它对应存的函数指针。**

### 4.4 "fd 可读"到底是什么意思

每个 fd 背后，内核都维护着一块"接收缓冲区"，暂存"还没被你 read() 走的数据"。

打比方：`fd` 就像信箱，内核是邮递员，不断地把信投进信箱（不管你在不在家）。**"可读"就是"信箱里现在有信，一开就能拿到，不用等"**。

**时间线示例**（fd=3 是网络连接，fd=5 是标准输入）：

```
T0：刚注册，两个fd的内核缓冲区都是空的
    fd=3 缓冲区: [ 空 ]
    fd=5 缓冲区: [ 空 ]

T1：调用 select(...)，线程睡眠，内核在这两个fd的缓冲区上"挂"了通知

T2：网络对端发来 "hello"，内核自动把数据搬进 fd=3 的缓冲区（此刻程序还在睡觉，不知情）
    fd=3 缓冲区: [ h e l l o ]
    fd=5 缓冲区: [ 空 ]
    → 内核发现fd=3从空变非空，唤醒正在等待的线程

T3：select 返回，readfds 位图里只有 fd=3 那一位是亮的

T4：FD_ISSET(3,...) 为真 → 调用 fd=3 对应的回调
    FD_ISSET(5,...) 为假 → 跳过

T5：回调里 read(fd, buf, 100) 之所以不会阻塞、能立刻拿到数据，
    正是因为 select 已经确认过"这个fd的缓冲区里有数据在等着"——
    read() 只是把内核缓冲区里已经攒好的数据"拷贝"到用户态的 buf 里
```

**一句话总结**：**"fd 可读" = "这个 fd 背后的内核接收缓冲区里现在有数据，调用 read() 能立刻拿到，不用傻等"。**

## 五、`select()` 这一行代码，从调用到返回的完整内存过程

```c
int ready = select(max_fd + 1, &readfds, NULL, NULL, &timeout);
```

### 5.1 参数传递方式：值传递 vs 地址传递

| 参数 | 传递方式 | select 能不能改到原始变量 |
|---|---|---|
| `max_fd + 1` | 值拷贝 | 不能，也不需要，只是告诉内核扫描范围 |
| `&readfds` | 地址 | **能**，内核直接改写这块内存 |
| `&timeout` | 地址 | **能**（部分系统实现会回写剩余时间） |
| 返回值 → `ready` | 值拷贝（通过寄存器） | 最终结果被拷贝进 ready |

`readfds` 和 `timeout` 必须传地址，因为 `select` 需要把结果**写回**给调用者；如果传值的拷贝，`select` 改的只是它自己的临时副本，函数一结束就没了，外面完全看不到变化。

### 5.2 调用前的栈内存布局（示意）

```
event_loop() 的栈帧
┌─────────┬────────────┬──────────────────────────────┐
│ 0x7000  │ readfds    │ [已用FD_SET点亮fd=0那一位]      │
│ 0x7080  │ max_fd     │ 0                              │
│ 0x7084  │ timeout    │ tv_sec=2, tv_usec=0             │
│ 0x708C  │ ready      │ ???（还没赋值）                  │
└─────────┴────────────┴──────────────────────────────┘
```

### 5.3 调用时传给内核的信息

```
nfds       = 1        （max_fd=0, 所以是0+1）
readfds    = 0x7000   ← readfds变量的地址
writefds   = NULL
exceptfds  = NULL
timeout    = 0x7084   ← timeout变量的地址
```

内核拿到的不是数据拷贝，而是"你的内存在哪"这个信息本身。

### 5.4 陷入内核、线程挂起

CPU 执行一条系统调用指令，把控制权交给内核。这一刻用户态代码"暂停"，但**栈帧不会消失** —— `0x7000` 到 `0x708C` 这块内存原封不动地留在那，内核知道"返回时要去哪儿找这块内存"，因为地址已经传给它了。

**"挂起"不等于"程序状态丢了"**：线程的执行进度（栈、变量、下一条该执行的指令/返回地址）被完整保留，一旦被唤醒就无缝从原来断点继续跑。这跟"多线程里另一个线程还在跑"是完全不同的两回事——单线程事件循环里，`select` 睡下去的时候，整条执行链是真的彻底停住的。

### 5.5 唤醒：内核直接改写传入的内存

**情况A：fd 就绪**（比如键盘来了输入）——内核跑到 `0x7000`，把没就绪的位清零，只留就绪的：
```
0x7000  readfds  →  [00000001]  （只有fd=0那一位还是1）
```

**情况B：超时**（2秒内没人就绪）——内核把 `readfds` 整个清空：
```
0x7000  readfds  →  [00000000]
```

### 5.6 返回值写入 `ready`

内核把这次调用的结果（就绪的fd个数，超时则是0）放进 CPU 寄存器，唤醒线程后，执行流从**发出系统调用指令的下一步**继续，寄存器里的值被拷贝进 `ready`：

```
0x708C  ready  →  1   （情况A：1个fd就绪）
或
0x708C  ready  →  0   （情况B：超时）
```

然后程序自然往下走，执行 `select` 这行代码下面的语句 —— **"醒来是从这一行下面开始执行"，这个理解是对的**。

## 六、`struct timeval` 与超时逻辑

### 6.1 `struct timeval` 结构

```c
struct timeval {
    long tv_sec;   // 秒
    long tv_usec;  // 微秒（百万分之一秒）
};
```

用两个整数（而不是一个浮点数）表示时间，是为了避免浮点数的精度误差。`tv_sec=2, tv_usec=0` 就是"整整2.000000秒"。

内存图（假设起始地址 0x7084）：
```
地址         成员         内容
┌──────────┬───────────┬────────┐
│ 0x7084   │ tv_sec    │   2    │
├──────────┼───────────┼────────┤
│ 0x708C   │ tv_usec   │   0    │
└──────────┴───────────┴────────┘
```

`timeout.tv_sec = 2` 本质就是"往地址0x7084写入整数2"——跟结构体数组赋值是同一套机制。

**注意事项**：Linux 的 `select` 返回后，`timeout` 可能被内核就地修改（尤其是提前因fd就绪而返回时，剩余时间不确定）。所以每轮循环开始时最好重新赋值 `tv_sec`/`tv_usec`，我们的代码里这两行赋值正好写在 `while(1)` 循环内部，所以是对的，不用担心这个坑。

### 6.2 `if (ready == 0)` 分支

`select` 返回值的含义：
- `ready > 0`：真有 fd 就绪了
- `ready == 0`：等到超时，一个 fd 都没就绪，是"时间到了"把线程叫醒的
- `ready < 0`：出错（这个最简模型暂不处理）

```c
if (ready == 0) {
    tick++;
    printf("[定时器] 第 %d 次 tick（2秒没有键盘输入）\n", tick);
    fflush(stdout);
    continue;
}
```

这段代码把 `select` 的"超时"机制，当成了一个简易的**定时器**使用——没有另开一个真正的定时器 API，只是复用了 `select` 本身"最多等多久"这个参数。

`continue` 的作用：跳过本次循环体剩下的代码，直接回到 `while(1)` 开头，开始下一轮。如果没有这个 `continue`，代码会继续走到下面的 `FD_ISSET` 检查，但因为超时时内核已经把 `readfds` 清空了，检查结果全是"没人就绪"，不会有任何副作用，只是白白多跑几行——加 `continue` 是更清晰、更省一点开销的写法。

## 七、`fflush` 与用户态/内核态缓冲

### 7.1 `printf` 不会立刻显示到屏幕

`printf` 只是把字符**先写进一块内存**——这块内存叫**标准输出缓冲区（stdout buffer）**。真正把这块内存内容"送出去"显示，是另一件事，叫 **flush（刷新）**。

这么设计是因为"每写一个字符就立刻跟内核打交道显示出来"代价很高（每次都要陷入内核），所以标准库选择"先攒一批，攒够了或者遇到特定条件再一次性送出去"，效率更高。

### 7.2 `fflush(stdout)` 做的事

> "别攒了，现在立刻把 buffer 里目前攒着的内容，一次性通过系统调用（如 write()）真正写出去，然后把缓冲区清空。"

### 7.3 用户态 / 内核态边界图

```
┌─────────────────────────────────────────┐
│              用户态（你的程序）              │
│  printf("...")                            │
│      ↓ 只是把字符拷贝进这块内存             │
│  ┌───────────────────────┐               │
│  │ stdout 的 buffer       │               │
│  │ [ "..." | "..." | 空 ] │  ← 数据待在这   │
│  └───────────────────────┘               │
└─────────────────────────────────────────┘
                    │
                    │ fflush(stdout) 触发 write() 系统调用，跨越边界
                    ▼
┌─────────────────────────────────────────┐
│              内核态                        │
│  内核拿到数据，操作终端驱动，显示到屏幕        │
└─────────────────────────────────────────┘
```

**关键点**：`printf` 调用完之后，数据**只在用户态**（这个进程自己的内存里），内核完全不知情，直到 `fflush`（或缓冲区攒满、或程序正常退出触发的隐式flush）才真正陷入内核。

这和 `select` 陷入内核是同一类机制——都是"用户态代码执行特殊指令，把控制权交给内核，请求内核做只有它有权限做的事"。区别是 `select` 陷入后可能长时间不返回（等条件满足），`write()` 陷入后通常很快返回。

### 7.4 对应我们踩过的坑

在非终端环境（比如管道、文件重定向）运行程序时，标准库会自动切换成"全缓冲"模式（攒满缓冲区或程序正常退出才自动刷新），而不是终端下"遇到换行符就自动刷新"的行缓冲模式。我们最初在沙盒里用管道喂输入测试时，程序被 `timeout` 硬杀（非正常退出），缓冲区里的数据从未被刷新，导致看起来"没有任何输出"。加上 `fflush(stdout)` 后，每条消息打印后立刻强制刷新，不管是不是终端环境都能看到。

## 八、`on_stdin_ready` 回调函数详解

```c
void on_stdin_ready(int fd)
{
    char buf[100];
    size_t n = read(fd, buf, sizeof(buf) - 1);
    if (n > 0)
    {
        buf[n - 1] = '\0'; // 去掉末尾的换行符
        printf("[事件] 收到键盘输入: \"%s\"\n", buf);
    }
}
```

### 8.1 `fd` 参数的值从哪来

在 `main` 里：`register_event(0, on_stdin_ready);` —— 这里的 `0` 就是**标准输入（stdin）的文件描述符编号**，这是 POSIX 系统的约定：

| fd 编号 | 代表什么 |
|---|---|
| 0 | 标准输入 stdin（默认键盘） |
| 1 | 标准输出 stdout（默认屏幕） |
| 2 | 标准错误 stderr（默认屏幕） |

这个 `0` 存进 `events[0].fd`，之后在事件循环里被原样取出，通过 `events[i].callback(events[i].fd)` 传回 `on_stdin_ready`，等价于直接调用 `on_stdin_ready(0)`。

### 8.2 逐行执行过程（以敲入 "xxz" + 回车为例）

```c
char buf[100];
```
栈上开辟100字节空数组，内容是垃圾数据。

```c
size_t n = read(fd, buf, sizeof(buf) - 1);
```
- `fd`（值为0）：从标准输入这个"信箱"读
- `buf`：数组退化成指针，告诉内核数据往这里放
- `sizeof(buf) - 1`：少读一个字节，留位置给字符串结束符 `\0`，防止越界

因为 `select` 已确认 fd=0 有数据，`read()` 不会阻塞，立刻把内核缓冲区里的数据拷贝进 `buf`，返回读到的字节数。敲 "xxz" + 回车，内核缓冲区是 `x x z \n`（4字节），`read` 返回4：

```
buf 数组
┌───┬───┬───┬───┬───┬─────────┐
│ x │ x │ z │\n │ ? │ ...(垃圾)│
└───┴───┴───┴───┴───┴─────────┘
  0   1   2   3   4
n = 4
```

```c
if (n > 0)
```
确认真读到了数据（n=0代表对方关闭，n<0代表出错，这个简化模型暂不处理这两种情况）。

```c
buf[n - 1] = '\0';
```
`n-1 = 3`，正是换行符 `\n` 所在的下标。把这个位置覆盖成 `'\0'`（字符串结束符）：

```
buf 数组
┌───┬───┬───┬───┬───┬─────────┐
│ x │ x │ z │\0 │ ? │ ...(垃圾)│
└───┴───┴───┴───┴───┴─────────┘
  0   1   2   3   4
```

C 语言"字符串"的规矩是：从某地址开始读，直到遇到 `'\0'` 为止，中间内容才是这个字符串。不做这一步，字符串末尾会带着看不见的换行符，打印会多出空行。

```c
printf("[事件] 收到键盘输入: \"%s\"\n", buf);
```
`%s` 从 `buf` 起始地址开始打印，遇到 `\0` 停下，正好打印出干净的 `"xxz"`。

函数结束后，`buf`、`n`、`fd` 这几个局部变量随着栈帧销毁而"消失"。

### 8.3 一句话总结

> `on_stdin_ready(0)` 做的事：从 fd=0（键盘）这个信箱，把已经等在内核缓冲区里的数据一次性取出放进自己的内存 `buf`，把末尾换行符换成字符串结束符，再打印出来。

## 九、Windows / MSVC 环境的坑（踩坑记录）

### 9.1 `#include <cstdio>` 报错 STL1003

`<cstdio>` 是 **C++ 专属头文件**（C++ 把 C 标准库头文件做了一份"去掉.h、加c前缀"的版本，对应 C 的 `<stdio.h>`）。`.c` 文件按C语言编译，include 这个头会一路扫进 MSVC 的 STL 实现内部，STL 内部检查"是否在C++环境"失败，报错 `Unexpected compiler, expected C++ compiler`。

**改法**：换成 `#include <stdio.h>`。

### 9.2 `__WSAFDIsSet` 链接错误（LNK2019）

如果用 `#include <winsock.h>` 在 Windows 上尝试用 `select`/`FD_ISSET`：`FD_ISSET` 这个宏在 Windows Winsock 实现下，背后会调用一个真正的函数 `__WSAFDIsSet`，这个函数的实现在 `ws2_32.lib` 库里。只 include 头文件（只拿到"声明"）而没有链接这个库，链接器就找不到函数实现，报 `unresolved external symbol`。

### 9.3 更本质的问题：Windows 的 select 只能用于 socket

即便解决了链接问题，**Windows（Winsock）的 `select()` 只能监听网络套接字（socket），不能监听标准输入（stdin）这类普通文件描述符**。`register_event(0, on_stdin_ready)` 在纯 Windows 环境下无法正常工作，因为 `0` 根本不是 Winsock 认识的 socket 句柄。

**结论**：`select`/`fd_set`/`read()` 这套是 POSIX（Linux/Unix）的世界观，跟 Windows 是完全不同的两套体系。

### 9.4 解决方案：改用 WSL

在 WSL（Windows 自带的 Linux 子系统）里，POSIX 的 `select`、`fd_set`、`read()` 原生可用，且能监听 stdin。

代码头文件改回：
```c
#include <stdio.h>
#include <unistd.h>
#include <sys/select.h>
```

访问 Windows 文件（无需真的复制）：
```bash
cd /mnt/c/Users/你的用户名/xxx/项目路径/src
gcc -o main main.c
./main
```

或者真正复制一份到 WSL 自己的文件系统（性能更好，推荐长期开发用）：
```bash
mkdir -p ~/eventloop
cp /mnt/c/Users/你的用户名/xxx/main.c ~/eventloop/
cd ~/eventloop
```

在 WSL 里实测运行成功：连续敲入多行文字，每行都立刻触发 `on_stdin_ready` 回调打印出来；若发呆超过2秒不碰键盘，会看到 `[定时器] tick` 输出。

## 十、目前为止的核心结论汇总

1. **阻塞** = 没数据就让当前线程傻等；**非阻塞** = 没数据立刻告知，自己决定接下来干嘛
2. 异步的本质不是"省CPU"，而是**用少量线程应付大量等待中的任务，不让一个任务的等待拖累其他任务**
3. `select`/`poll`/`epoll` 让一个线程能"同时守候"一批 fd，谁先就绪就处理谁，是事件循环的地基
4. 事件循环骨架 = 注册事件（fd+回调，用函数指针存起来）→ 循环等待（select）→ 谁好了调用谁的回调
5. "fd 可读" = 这个 fd 背后内核维护的接收缓冲区里已经有数据，`read()` 能立刻拿到不用等
6. `select` 挂起时，线程的执行进度（栈、变量、返回地址）被完整保留，被唤醒后从断点无缝继续，这跟多线程"另一个线程还在跑"是完全不同的两回事
7. `select` 的超时参数，可以被复用当作一个简易定时器；`ready==0` 就是"超时唤醒，没有fd真正就绪"的信号
8. `printf` 先把数据写进用户态的 stdout 缓冲区，`fflush` 才会触发系统调用把数据真正交给内核显示出来
9. `select`/`fd_set`/`read()` 是 POSIX 世界观，Windows 原生不支持（Winsock 的 select 仅限 socket），需要用 WSL 保持一致的学习路径
