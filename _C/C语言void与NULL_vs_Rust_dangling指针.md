# C 的 `void`/`NULL` 与 Rust 的 dangling pointer：完整对比笔记

---

## 一、C 中的 `void`

`void` 不是一个"值"，而是一个**类型标记**，表示"没有类型"。它有三种典型用法：

### 1.1 函数签名中：表示"无"

```c
void foo(void);        // 不接受参数、不返回值
int  bar(void);         // 不接受参数，返回 int
void baz(int x);        // 不返回值，接受一个 int
```

### 1.2 `void*`：无类型指针

```c
void *p;   // p 只存一个地址，编译器不知道这块内存该按什么类型解读
```

`void*` 只携带**地址信息**，不携带**类型信息**。因此：

- 不能直接解引用：`*p` 是非法的（编译器不知道读几个字节、怎么解释这些字节）
- 使用前必须先转型：`int *ip = (int*)p;`
- 任何类型指针 → `void*`：**隐式转换合法**（C 语言层面）
- `void*` → 任意类型指针：C 里也**隐式合法**（但 C++ 里必须显式 cast，这是 C 和 C++ 一个明确的语法差异）

```
 内存视角：
 ┌──────────────┐
 │ void *p ──────┼──▶ [??  ??  ??  ??]   编译器不知道这4字节是 int？float？struct的一部分？
 └──────────────┘
```

## 二、C 中的 `NULL`

`NULL` 是一个**宏**，语义是"空指针常量"——即"这个指针不指向任何有效对象"。

```c
#define NULL ((void*)0)   // 常见实现之一，具体写法因标准库实现而异
```

### 2.1 三个容易混淆的点

| 误解 | 正确理解 |
|---|---|
| "NULL 就是数字0" | NULL 是**指针类型**的字面值，只是**源码里写作 0**，编译器负责把它翻译成"该平台代表空指针的位模式" |
| "空指针的内存表示一定是全0" | 在 x86 / ARM 等**几乎所有现实平台**上确实是全0，但 **C 标准本身没有强制规定这一点**（历史上存在过极少数例外架构，现实工程中基本不用操心） |
| "对 NULL 判断用 `p == 0` 和 `p == NULL` 没区别" | 效果一样，但 `NULL` 语义更清晰，是惯用写法 |

### 2.2 判空写法

```c
if (p == NULL) { ... }   // 显式
if (!p)        { ... }   // 简写，等价
```

### 2.3 对 NULL 解引用/运算 = 未定义行为（UB）

```c
int *p = NULL;
*p = 5;        // UB，通常段错误崩溃
p + 1;         // 同样是 UB —— 容易被忽略！C标准规定只有对"合法数组内的指针（含尾后指针）"
               // 做算术运算才是良定义的，NULL 不属于任何数组，对它做 +1 严格来说是 UB
```

## 三、`int x = 0` vs `int *p = NULL`：内存 vs 类型的对比

```c
int  x = 0;       // 一个普通整数
int *p = NULL;    // 一个指针，恰好数值也是"空"
```

```
 内存位模式（绝大多数现实平台，如 x86-64）：

 x (int, 4字节)        p (指针, 64位系统上8字节)
 ┌──┬──┬──┬──┐         ┌──┬──┬──┬──┬──┬──┬──┬──┐
 │00│00│00│00│         │00│00│00│00│00│00│00│00│
 └──┴──┴──┴──┘         └──┴──┴──┴──┴──┴──┴──┴──┘
   位模式一样是"全0"       但【宽度不同】(4字节 vs 8字节，取决于平台)
```

| | `int x = 0` | `int *p = NULL` |
|---|---|---|
| 编译器视角 | 整数类型 | 指针类型 |
| 内存位模式（现实平台） | 全0 | 全0（标准未强制保证，但现实平台通行） |
| 占用宽度 | `sizeof(int)`，通常4字节 | `sizeof(指针)`，32位系统4字节/64位系统8字节 |
| 语义 | 数值"零" | "不指向任何对象" |
| `x == p` 能直接比较吗 | **不能**，类型不匹配（编译器报错/警告） |

**核心结论**：两者位模式的"巧合相同"只是**实现细节**，语言的**类型系统在编译期就把它们隔离开**，不会互相污染语义。这是静态类型语言的意义所在——"是不是指针"这件事不取决于内存里的比特是什么，而取决于**编译器如何标注这个变量的类型**。

## 四、和 Rust 的 dangling pointer 是一回事吗？—— **不是，思路是反着来的**

### 4.1 C 的逻辑 vs Rust 的逻辑

```
C 的逻辑：
  "没有数据" ──▶ 让指针 = NULL（值为0）
  判断方式：if (p == NULL)

Rust 的逻辑：
  &T / Box<T> / NonNull<T> 这类类型有一条【编译器强制的不变量】：
      "指针字段永远不能是空的"
  于是"没有数据"这件事，【不能】用指针本身的值来表达
  只能靠旁边一个独立的字段（比如 len）来表达
```

### 4.2 为什么 Rust 要这么设计？——niche optimization

正因为 `NonNull<T>` 承诺"永远非空"，Rust 才能做这样的内存优化：

```rust
size_of::<Box<i32>>()          // 8 字节（64位系统上一个指针的大小）
size_of::<Option<Box<i32>>>()  // 同样是 8 字节！不需要额外的1字节做标志位
```

```
 原理示意：
 Box<T> 的合法取值范围里，【空指针这个位模式永远不会出现】
 → 这个"空缺"的位模式正好可以复用来表示 Option 的 None
 → 不需要额外分配一个 bool/tag 字段

 Option<Box<T>>:
   Some(box) ──▶ [真实的、非空的指针]
   None      ──▶ [复用"不可能出现"的空指针位模式]
```

### 4.3 `Vec::new()` 这类"零容量容器"怎么办？

`Vec<T>` 内部有个指针字段，但 `Vec::new()` 时**还没做任何堆分配**，这个指针**不能是空指针**（违反不变量），标准库的做法是：

```rust
NonNull::dangling()   // 返回一个【非空、但不指向任何真实分配内存】的占位指针
```

这个地址的具体数值 = `align_of::<T>()`（`T` 类型的对齐要求），比如：

```rust
NonNull::<u8>::dangling()   // 地址数值 = 1
NonNull::<i32>::dangling()  // 地址数值 = 4
NonNull::<u64>::dangling()  // 地址数值 = 8
```

**关键点**：它满足"非空"这个**类型系统层面的语法要求**，但**语义上完全不指向任何合法内存**——一旦真的解引用它，就是 UB，危险程度和 C 里对野指针解引用完全一样。

### 4.4 一张表总结两者的本质差异

| | C 的 `NULL` | Rust 的 `NonNull::dangling()` |
|---|---|---|
| 数值 | 通常是 0 | 非0（对齐值，≥1） |
| 用途 | 显式表示"这就是空" | 满足"指针字段不能为空"这条类型系统约束，本身不承载"有没有数据"的语义 |
| 能否靠指针值本身判空 | **可以**：`p == NULL` | **不行**！它看起来就是个"合法非空指针"，必须靠旁边的 `len`/`capacity` 字段来判断"其实没数据" |
| 能否解引用 | 不能（UB） | 不能（UB） |
| "有没有数据"这个信息存在哪 | 指针本身的值 | 指针**旁边**独立的长度/容量字段 |

**一句话概括**：C 把"有没有数据"这个信息**编码进指针的值**里（0 就是没有）；Rust 把这个信息**从指针里剥离出来**，交给旁边的字段去管，指针字段永远保持"类型合法但不能碰"的状态——这是为了不破坏"指针永不为空"这条编译器要依赖的硬性保证。

## 五、扩展 / 容易被忽略的知识点

### 5.1 C 里"指针失效"其实有三种，容易被统称为"空指针"

```
1. 空指针 (null pointer)     —— 明确赋值为 NULL，可检测
2. 野指针 (wild pointer)     —— 声明后从未初始化，值是随机的栈垃圾，【无法通过判空发现】
3. 悬空指针 (dangling pointer) —— 曾经合法，但指向的内存已被 free()，指针本身没有被
                                手动清空，【看起来仍像"合法非空指针"】

int *p1 = NULL;      // 空指针，安全，可判断
int *p2;             // 野指针！! 危险，值是垃圾内存，不会==NULL
int *p3 = malloc(4);
free(p3);            // p3 现在是悬空指针！内存已释放，但 p3 的值没变，看着还"非空"
```

> **注意**：C 里的"悬空指针（dangling pointer）"和上面 Rust 的 `NonNull::dangling()` **共享"dangling"这个词，但含义完全不同**，是本笔记里最容易搞混的一个点：
> - C 的 dangling pointer：**曾经合法**，因为**生命周期结束后没有清理**才变得危险（use-after-free 的产物）
> - Rust API 里的 `dangling()`：**从来没有合法过**，是刻意构造的、专门用于**从不会被解引用**的占位符，是主动设计出来的"安全的假指针"，本质上和 use-after-free 没有关系

这一点很重要：**Rust 真正要防的"悬垂引用"（对应 C 的第三种 dangling pointer）是靠 borrow checker 在编译期杜绝的**，`NonNull::dangling()` 只是标准库内部实现细节里借用了同一个单词，两者不要混为一谈。

### 5.2 C++11 引入 `nullptr` 就是为了修复 `NULL` 的一个历史遗留问题

```c++
void f(int);
void f(char*);

f(NULL);   // C++里 NULL 常被定义成字面量 0（纯int），
           // 重载决议时会匹配到 f(int) 而不是 f(char*)，这通常不是程序员想要的结果！

f(nullptr); // C++11 起，nullptr 是专门的指针字面量类型 std::nullptr_t，
            // 编译器能正确匹配到 f(char*)，消除了这个歧义
```

这也侧面说明：`NULL` 本质上"只是碰巧等于0的一个宏"，在类型系统更严格的 C++ 里，这种"用整数字面量伪装指针"的做法反而成了坑，所以才被 `nullptr` 取代。

### 5.3 `calloc` 对指针数组清零 = 产生一批"合法的NULL"，这是 C 标准明确保证的

```c
int *arr[10] = { 0 };        // 或
int **arr = calloc(10, sizeof(int*));
// C 标准保证：全0字节的指针，在【绝大多数】平台上等价于 NULL
// （这是极少数 C 标准里"把位模式全0"和"空指针"直接挂钩的实用场景）
```

这是实践中一个很常用但很少被解释清楚的技巧：初始化一堆指针为"全0内存"，绝大多数场景下等价于把它们都设为 NULL。

### 5.4 零大小类型（ZST）在 Rust 里让"dangling"更微妙

```rust
align_of::<()>()   // = 1，不是 0
```

`()` 这种零大小类型，它的"dangling"占位地址是 1，而不是 0——再次印证：Rust 从设计层面**排除了地址为0的可能性**，不是运气好没撞上，而是语言规范里**对齐值下限被硬性规定为 ≥1**，这是根本原因。

### 5.5 函数指针 vs 数据指针，`void*` 未必能安全承载函数指针

```c
void *p = (void*)main;   // 把函数指针转成 void*
```

C 标准**并不保证**数据指针（`void*`）和函数指针的大小/表示方式一定相同——理论上存在两者不能安全互转的平台。POSIX 标准专门为了兼容 `dlsym()` 这类需要把函数指针塞进 `void*` 的场景，额外放宽了这条规则。这属于比较冷门的边界情况，日常写业务代码基本不会遇到，但如果你以后读系统编程/POSIX相关的源码，看到类似警告注释会知道背景。

## 七、一句话总结全文

- **C**：用指针的**值本身**（是否为0）来编码"有没有数据"，简单直接，但把安全责任完全交给程序员。
- **Rust**：把"有没有数据"这个信息从指针值里**剥离**出来，交给外部的长度字段管理，指针字段本身永远保持"类型上合法、语义上不可碰"的状态，以此换取编译器能做的更多安全保证和内存优化（niche optimization）。
- 两者的"空/悬空"概念名字相似（NULL / dangling），但**解决的问题、设计动机、检测方式完全不同**，是本笔记里最容易踩坑的混淆点。
