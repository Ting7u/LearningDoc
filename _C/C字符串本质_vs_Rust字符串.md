# C 字符串的本质 vs Rust 字符串：完整对比笔记

---

## 一、C 字符串的本质：**它根本不是一个"类型"**

这是理解 C 字符串最关键的一点：**C 语言里没有"字符串类型"这回事**。所谓"字符串"，只是一种**社区约定**（convention）：

> 一段连续的 `char` 内存，以字节值 `\0`（数值0）作为"结束标记"。

```c
char s[] = "hello";
```

在编译器眼里，`s` 就是一个普通的 `char` 数组，仅此而已。"这是一个字符串"这件事，完全是**程序员和标准库函数之间的默契**，编译器本身并不知道、也不检查这个数组里有没有 `\0`。

### 1.1 内存布局

```c
char s[] = "hello";
```

```
 内存视角：
 ┌────┬────┬────┬────┬────┬────┐
 │ h  │ e  │ l  │ l  │ o  │ \0 │
 └────┴────┴────┴────┴────┴────┘
   0x00  0x01  0x02  0x03  0x04  0x05    ← 地址偏移
 数组实际大小 = 6 字节（5个字符 + 1个结束符），不是5

 s 是数组名，退化(decay)成指向首元素的指针：s == &s[0]
```

**关键点**：这个数组里**没有任何地方记录"长度是5"**。要知道长度，唯一办法是**从头扫描到 `\0`**：

```c
size_t strlen(const char *s) {
    const char *p = s;
    while (*p != '\0') p++;   // 必须逐字节扫描，O(n)
    return p - s;
}
```

这就是为什么 `strlen()` 是 **O(n)** 操作——它每次都要重新数一遍，C 标准库不会替你"记住"长度。

## 二、字符串字面量：`char*` vs `char[]` 的关键区别

这是一个新手极易踩坑、但很少被讲透的点：

```c
char  arr[] = "hello";   // ① 数组
char *ptr   = "hello";   // ② 指针指向字面量
```

```
 情况①：char arr[] = "hello";
 ┌───────────────────────────────┐
 │ 栈 (stack)                      │
 │  arr: [h][e][l][l][o][\0]      │  ← 字符串内容被【拷贝】进这块可写内存
 └───────────────────────────────┘
 arr[0] = 'H';   // 合法！可以修改

 情况②：char *ptr = "hello";
 ┌──────────────┐        ┌────────────────────────────┐
 │ 栈            │        │ 只读数据段 (.rodata)          │
 │ ptr ─────────┼───────▶│ [h][e][l][l][o][\0]         │
 └──────────────┘        └────────────────────────────┘
 ptr[0] = 'H';   // 【未定义行为】！试图写只读内存，通常段错误崩溃
```

| | `char arr[] = "hello"` | `char *ptr = "hello"` |
|---|---|---|
| 字面量内容存在哪 | 拷贝到 `arr` 所在的可写内存（栈/静态区） | 存在只读数据段，`ptr` 只是指向它的地址 |
| 能否修改内容 | 可以 | **不能**，修改是 UB |
| `sizeof` | `sizeof(arr)` = 6（数组大小） | `sizeof(ptr)` = 指针大小（如8） |

**很多新手 bug 的根源**：把字面量赋给 `char*` 之后尝试修改，代码"看起来"完全正常，但实际是 UB，某些平台/编译器优化下会直接崩溃，另一些平台又"侥幸"能跑——这也是"未定义行为不代表一定报错，而是行为不可预测"的典型例子。

## 三、C 字符串操作为什么天生危险

因为**长度信息不存在数组里，全靠程序员自己管**，标准库函数默认相信你给的缓冲区足够大：

```c
char buf[5];
strcpy(buf, "hello world");   // 源字符串12字节(含\0)，目标只有5字节
                                // 【缓冲区溢出】，覆盖了buf之后的内存
                                // 这是C历史上无数安全漏洞的根源
                                // (从 Morris蠕虫 到现代很多 CVE 都是这个模式)
```

```
 buf 只有5字节，strcpy 却往里写12字节：

 ┌────┬────┬────┬────┬────┐┌──────────────────────┐
 │ h  │ e  │ l  │ l  │ o  ││ 越界写入了相邻内存!!   │
 └────┴────┴────┴────┴────┘└──────────────────────┘
   buf 的合法范围            ← 栈上其他变量/返回地址可能被覆盖
```

这也是为什么现代 C 代码规范会强烈建议用 `strncpy`/`snprintf` 等**限长版本**，以及为什么很多"内存安全语言"（Rust、Go等）出现的核心动机之一，就是要**从根本上杜绝这类"长度信息丢失导致越界"的错误**。

## 四、Rust 的字符串：`String` 与 `&str`

Rust 里字符串**不是一个约定，而是真正的类型**，而且分成两种，分工明确：

### 4.1 `&str`：字符串切片（borrowed，不可增长）

```rust
let s: &str = "hello";
```

`&str` 是一个**胖指针（fat pointer）**：不只存地址，还**显式存了长度**。

```
 &str 的内存布局（64位系统上，共16字节）：

 ┌──────────────┬──────────────┐
 │ ptr (8字节)   │ len (8字节)   │
 └──────┬───────┴──────────────┘
        │
        ▼
   [h][e][l][l][o]     ← 指向的数据，【没有 \0 结尾】
```

**没有结束符，长度是独立字段**——这是和 C 字符串最本质的区别，稍后详细对比。

### 4.2 `String`：拥有所有权的、可增长的字符串（heap-allocated）

```rust
let mut s: String = String::from("hello");
s.push_str(", world");
```

`String` 本质上是 **`Vec<u8>` 的一层包装**，内部结构：

```
 String 的内存布局（64位系统上，共24字节，栈上）：

 ┌──────────────┬──────────────┬──────────────┐
 │ ptr (8字节)   │ len (8字节)   │ capacity(8字节)│
 └──────┬───────┴──────────────┴──────────────┘
        │
        ▼   (堆上分配的实际数据)
   [h][e][l][l][o][,][ ][w][o][r][l][d]
    ← len=12 →              ← 未用到的预留容量 →
    ←──────────── capacity ────────────→
```

- `len`：当前实际使用的字节数
- `capacity`：堆上实际分配的空间（为了 `push_str` 这类追加操作，避免每次都重新分配）
- **依然没有 `\0` 结束符**，`String` 完全靠 `len` 字段知道自己有多长

## 五、核心对比：隐式终止符 vs 显式长度字段

这一点其实和我们之前聊 `NULL` / Rust dangling pointer 时的思路**是同一个主题的延续**：

> C 习惯把"元信息"（长度/是否为空）**编码进数据本身**（用特殊值 `\0`/`NULL` 当哨兵）；
> Rust 习惯把"元信息"**拆分成独立字段**（`len`），数据本身只是纯数据，不承担"标记结束"的语义。

| | C 字符串 | Rust `String`/`&str` |
|---|---|---|
| 长度信息存哪 | **不存**，靠扫描 `\0` 现算 | **显式存储**在 `len` 字段 |
| 求长度复杂度 | `strlen()` = **O(n)** | `.len()` = **O(1)**，直接读字段 |
| 能否包含字节值为0的内容 | **不能**，0会被当成"字符串已结束" | **可以**！`\0` 只是普通字节，不影响长度判断 |
| 编码要求 | 无强制要求（可以是ASCII/GBK/任意字节序列，C不关心） | **强制合法 UTF-8**，由类型系统保证 |
| 越界风险 | 高（长度靠人管，标准库函数默认信任调用者） | 低（长度是类型自带信息，标准库函数据此自动检查边界） |

**举一个能直观体会差异的例子**——包含空字节的"字符串"：

```c
// C：这是一场灾难
char buf[] = {'a', 'b', '\0', 'c', 'd'};
printf("%s\n", buf);       // 只会打印 "ab"，\0 之后的 "cd" 完全"消失"
strlen(buf);                // 返回 2，不是 5
```

```rust
// Rust：完全没问题，因为长度不靠扫描字节内容
let s = String::from("ab\0cd");
println!("{}", s.len());   // 输出 6（"ab\0cd" 的UTF-8字节数，中间的\0只是普通字节）
println!("{}", s);          // 完整打印所有内容（终端显示上\0可能不可见，但数据完整存在）
```

## 六、扩展 / 容易被忽略的知识点

### 6.1 Rust 字符串按"字节"索引，不能直接用下标取字符

```rust
let s = "你好";
// s[0]   // 【编译错误】！&str 不支持整数下标索引
```

原因：Rust 字符串**保证是合法 UTF-8**，而 UTF-8 是**变长编码**——一个汉字通常占 **3 个字节**，如果允许 `s[0]`，你很可能切在一个字符的"中间"，切出一段无效的 UTF-8 字节，这在类型系统层面是不允许存在的（`&str`/`String` 的核心不变量就是"永远合法UTF-8"）。

```rust
let s = "你好";
println!("{}", s.len());              // 6  ← 字节长度（两个汉字各3字节）
println!("{}", s.chars().count());    // 2  ← 字符个数，需要显式调用 .chars() 遍历
```

```
 "你好" 的字节布局（UTF-8编码）：
 ┌────┬────┬────┬────┬────┬────┐
 │0xE4│0xBD│0xA0│0xE5│0xA5│0xBD│   ← "你" 3字节 + "好" 3字节
 └────┴────┴────┴────┴────┴────┘
  s.len() 数的是这6个字节，不是"2个字"
```

而 C 里对多字节字符集（如 GBK、UTF-8）**没有任何语言层面的感知**——`char` 就是1字节，一个汉字在 C 眼里就是"两三个独立的、互不相关的 char"，`strlen` 数出来的是字节数，程序员需要自己用额外的库（如 `iconv`/宽字符 `wchar_t`）去处理多字节语义，语言本身不管这件事。

### 6.2 越界切片会在【运行时】panic，不是静默出错

```rust
let s = "你好";
let bad = &s[0..1];   // 【运行时 panic】："byte index 1 is not a char boundary"
```

Rust 检测到这次切片切在了字符中间，**主动崩溃**而不是像 C 那样"悄悄给你一段乱码/无效数据"。这是"宁可显式崩溃，也不允许出现不变量被破坏的数据"这一设计哲学的体现——和 dangling pointer 一节里"违反不变量必须在类型系统层面被禁止"是同一个思路的延伸。

### 6.3 一个常见误解：Rust 的 `String` 有 SSO（小字符串优化）吗？

**没有。** 这是从 C++ 转过来的人很容易带错的假设——C++ 的 `std::string` 通常有 SSO（短字符串直接存在栈上，不触发堆分配），但 **Rust 标准库的 `String` 没有做这个优化**，哪怕只存一个字符，也会触发一次堆分配（`malloc`）。这是 Rust 标准库一个明确的设计取舍，社区里有第三方 crate（如 `smartstring`、`compact_str`）专门补这个能力。

### 6.4 C 字符串跨语言互操作：Rust 的 `CString` / `CStr`

因为 C 生态里"字符串=以`\0`结尾的字节数组"是全球通用的约定，Rust 做 FFI（调用C库）时必须专门提供兼容类型：

```rust
use std::ffi::{CString, CStr};

let c_string = CString::new("hello").unwrap();  // 生成带\0结尾的、兼容C的字节序列
// 如果原字符串内部就包含 \0，CString::new 会返回 Err，
// 因为这种字符串根本无法用"\0结尾"的方式正确表达——这里能看出两种字符串模型的根本冲突

let c_str: &CStr = unsafe { CStr::from_ptr(some_c_pointer) };  // 反向：从C指针读取
```

这一段其实完美体现了本笔记的核心主题：**"隐式终止符"和"显式长度"是两套不兼容的元信息编码方式**，`CString`/`CStr` 存在的意义，就是在两套体系之间做一次显式的"翻译层"。

## 八、一句话总结全文

- **C 字符串**：没有真正的"字符串类型"，只是 `char` 数组 + "以 `\0` 结尾"的**纯人为约定**，长度靠**每次现场扫描**得到，语言本身不提供任何边界保护，这是几十年来大量安全漏洞的根源。
- **Rust 字符串**：`&str`/`String` 是**真正的类型**，把"长度"这个元信息**显式存成独立字段**，并且在类型系统层面**强制保证内容永远是合法 UTF-8**，代价是标准库不做 SSO 优化、且必须靠 `CString`/`CStr` 这类适配层才能和 C 生态互通。
- 这背后的设计哲学和我们之前讨论 `NULL`/`dangling pointer` 时的结论**完全一致**：C 倾向于**用特殊值当哨兵**、把元信息藏进数据本身；Rust 倾向于**把元信息拆成显式的独立字段**，让编译器能在类型层面做更多校验和优化。
