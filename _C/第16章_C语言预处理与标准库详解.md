## 1. 编译的四个阶段与预处理器的位置

理解预处理指令，首先要知道它在整个编译流程中的**位置**——它是**纯文本替换**阶段，发生在真正的 C 语法分析之前，对 C 语法一无所知。

```
源代码 (.c)
    │
    ▼
┌─────────────────────────┐
│ 1. 预处理 (Preprocessing) │  ← #include 展开、宏替换、条件编译裁剪
│   cpp / cc1 -E           │     产物：纯 C 代码，无任何 # 指令
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ 2. 编译 (Compilation)    │  ← 词法分析→语法分析→语义分析→生成汇编
│   词法/语法/语义检查      │
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ 3. 汇编 (Assembly)       │  ← 汇编代码 → 目标文件 (.o)
└─────────────────────────┘
    │
    ▼
┌─────────────────────────┐
│ 4. 链接 (Linking)        │  ← 多个 .o + 库 → 可执行文件
└─────────────────────────┘
```

关键点：预处理器**不理解**类型、作用域、语义，它只做**记号（token）级别的文本替换**。你可以用 `gcc -E file.c` 亲眼看到预处理后的结果——所有宏都被展开、所有 `#include` 都被内联进来。

```bash
gcc -E main.c -o main.i   # 只做预处理，生成中间文件 main.i
```

## 2. 预处理指令详解

### 2.1 `#include` —— 文本级别的"复制粘贴"

```c
#include <stdio.h>   // 尖括号：编译器在"系统头文件搜索路径"中找
#include "myutil.h"  // 双引号：先在当前文件所在目录找，找不到再找系统路径
```

`#include` 的本质是：**把目标文件的全部内容原封不动地粘贴到当前位置**。这也是为什么头文件必须做**重复包含保护**（见下文 `#ifndef`），否则同一个声明会被粘贴两次导致重定义错误。

```
foo.h 内容：int x;
bar.c: #include "foo.h"
       #include "foo.h"   // 如果没有保护，等价于写了两遍 int x; → 编译错误
```

### 2.2 `#define` —— 宏定义

两种形态：

**对象宏（object-like macro）**：简单的常量替换

```c
#define PI 3.14159
#define MAX_LEN 100
#define BUFFER_SIZE (MAX_LEN * 2)   // 注意：整体加括号，防止运算符优先级坑
```

**函数式宏（function-like macro）**：见第 3 节，坑更多。

**特殊运算符**：
- `#`（字符串化，stringizing）：把宏参数转成字符串字面量

```c
#define STR(x) #x
STR(hello)      // 展开为 "hello"
STR(3 + 4)      // 展开为 "3 + 4"（原样加引号，不计算）
```

- `##`（记号粘贴，token pasting）：把两个记号拼接成一个新记号

```c
#define CONCAT(a, b) a##b
int CONCAT(my, Var) = 10;   // 展开为 int myVar = 10;
```

底层原理：`##` 是在**宏展开阶段**、参数替换**之前**的记号流上做拼接，拼接后的结果必须是一个合法的记号（比如两个标识符拼成一个新标识符），否则是未定义行为。

**可变参数宏（C99 起）**：

```c
#define LOG(fmt, ...) printf("[LOG] " fmt "\n", __VA_ARGS__)
LOG("value = %d", x);
// 展开为：printf("[LOG] " "value = %d" "\n", x);
// 相邻字符串字面量会被编译器自动拼接（string literal concatenation）
```

`__VA_ARGS__` 代表 `...` 匹配到的所有剩余参数。GNU 扩展支持 `##__VA_ARGS__`（当没有可变参数时自动吃掉前面的逗号），C23 标准化了 `__VA_OPT__`。

### 2.3 `#ifdef` / `#ifndef` / `#else` / `#endif` —— 条件编译

```c
#ifndef MYHEADER_H
#define MYHEADER_H

// 头文件内容...

#endif // MYHEADER_H
```

这是经典的**头文件保护（include guard）**，逻辑是：

```
预处理器读到 #ifndef MYHEADER_H
   │
   ├─ 第一次包含：MYHEADER_H 未定义
   │      → 执行 #define MYHEADER_H
   │      → 编译头文件正文
   │      → 遇到 #endif 结束
   │
   └─ 第二次包含（同一编译单元）：MYHEADER_H 已定义
          → 跳过整个 #ifndef...#endif 之间的内容
```

现代编译器普遍支持 `#pragma once` 作为替代（见下），但 `#ifndef` 写法是**标准 C**，可移植性更好。

`#ifdef X` 等价于 `#if defined(X)`；`#ifndef X` 等价于 `#if !defined(X)`。

典型用途：平台相关代码

```c
#ifdef _WIN32
    #include <windows.h>
#elif defined(__linux__)
    #include <unistd.h>
#else
    #error "Unsupported platform"
#endif
```

### 2.4 `#if` / `#elif` —— 基于常量表达式的条件编译

与 `#ifdef` 不同，`#if` 后面跟的是一个**整数常量表达式**，可以做算术、逻辑、比较运算：

```c
#define VERSION 3

#if VERSION >= 3
    void newFeature(void);
#elif VERSION == 2
    void oldFeature(void);
#else
    #error "Version too old, please upgrade"
#endif
```

注意：`#if` 中未定义的标识符会被当作 `0`（这一点和普通 C 代码不同，普通代码里用未声明的标识符是编译错误）。

### 2.5 `#error` —— 主动报错

```c
#if !defined(__STDC_VERSION__) || __STDC_VERSION__ < 201112L
#error "This code requires C11 or later"
#endif
```

编译期直接终止编译并输出指定信息，常用于**前置条件校验**（编译器版本、宏配置冲突等），避免用户拿到一堆莫名其妙的后续错误。

### 2.6 `#pragma` —— 编译器专有指令

`#pragma` 不是标准化的具体行为，而是给**编译器实现**发消息的"信箱"，具体支持哪些 pragma、怎么解释，完全取决于编译器。以下举例说明常见用法，**但这些是特定编译器（GCC/Clang/MSVC）的扩展，不是 ISO C 标准保证的行为**：

```c
#pragma once                    // 非标准但被主流编译器广泛支持：头文件只包含一次

#pragma pack(push, 1)           // 常见于 GCC/MSVC：结构体按 1 字节对齐，不留 padding
struct Packet {
    char type;
    int  value;
};
#pragma pack(pop)

#pragma GCC diagnostic push     // GCC 专有：临时屏蔽某类警告
#pragma GCC diagnostic ignored "-Wunused-variable"
int unused_var;
#pragma GCC diagnostic pop
```

如果编译器不认识某个 `#pragma`，标准规定它应该**忽略**该行而不是报错——这是 `#pragma` 与 `#error` 的本质区别之一。

### 2.7 `#line` —— 修改行号/文件名记录

```c
#line 100 "generated.c"
// 从这一行开始，编译器认为当前是 "generated.c" 的第 100 行
```

这会影响 `__LINE__` 和 `__FILE__` 这两个预定义宏的值，从而影响编译警告/错误信息里显示的位置，以及 `assert()` 失败时打印的位置。**典型使用场景**：代码生成工具（比如 `yacc`/`bison` 生成的 `.c` 文件）想让报错信息指向"原始的 .y 文件"而不是生成出来的中间 `.c` 文件。手写代码里几乎用不到。

## 3. 函数式宏、副作用与条件编译陷阱

### 3.1 为什么函数式宏必须"里三层外三层"加括号

```c
#define SQUARE(x) x * x

int a = 100 / SQUARE(2);
// 天真地想：100 / (2*2) = 25
// 实际展开：100 / 2 * 2 = (100/2) * 2 = 100   ← 完全不是你想要的
```

正确写法：

```c
#define SQUARE(x) ((x) * (x))

int a = 100 / SQUARE(2);
// 展开：100 / ((2) * (2)) = 25   ✓
```

**为什么要给参数和整体都加括号**？因为宏展开是纯文本替换，不考虑运算符优先级。参数本身可能是一个复杂表达式：

```c
SQUARE(1 + 2)
// 若宏是 #define SQUARE(x) x*x         → 展开为 1 + 2*1 + 2 = 5（错！）
// 若宏是 #define SQUARE(x) (x)*(x)     → 展开为 (1+2)*(1+2) = 9（对）
```

### 3.2 副作用陷阱

```c
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int i = 5;
int m = MAX(i++, 10);
// 展开为：((i++) > (10) ? (i++) : (10))
// i++ 被求值了两次！结果依赖具体求值路径，且 i 被自增了两次
```

这是函数式宏和真正函数的**本质区别之一**：函数调用时参数只求值一次，宏展开时参数在文本中出现几次就被求值几次。这也是 C++ 更推荐用 `inline` 函数、模板代替宏的原因之一（C 里没有模板，但也应尽量用真函数替代复杂逻辑宏）。

### 3.3 条件编译的典型工程用法

- **平台/编译器适配**（前面已举例）
- **调试代码开关**：

```c
#ifdef DEBUG
    #define DBG_PRINT(...) fprintf(stderr, __VA_ARGS__)
#else
    #define DBG_PRINT(...) ((void)0)   // 发布版里彻底消失，零开销
#endif
```

- **特性开关（feature flag）**：控制某段代码是否编译进最终产物，常见于跨版本兼容的库代码。

## 4. C11 关键字：`_Generic` / `_Noreturn` / `_Static_assert`

### 4.1 `_Static_assert` —— 编译期断言

```c
_Static_assert(sizeof(int) == 4, "int 必须是 4 字节");

struct Point { int x, y; };
_Static_assert(sizeof(struct Point) == 8, "Point 大小不符预期");
```

- 只能用**常量表达式**，在**编译期**求值，不产生任何运行时代码（对比 `assert()` 是运行时检查，产生实际的条件跳转指令）。
- 可以出现在**文件作用域、块作用域、结构体内部**（C11 起，结构体内部的静态断言是允许的）。
- C11 标准要求**必须**提供诊断消息字符串；`<assert.h>` 定义了不带下划线的宏 `static_assert`，等价于 `_Static_assert`。
- 我记得 **C23** 放宽为消息可省略（单参数形式），但具体标准条款编号我没有把握完全准确，建议以 cppreference 或标准文本为准。

**用途举例**：跨平台代码里确保类型大小、结构体布局符合协议要求，一旦不满足直接在编译期报错，而不是等到运行时才发现数据错乱。

### 4.2 `_Noreturn` —— 声明函数不会返回

```c
_Noreturn void fatal_error(const char *msg) {
    fprintf(stderr, "Fatal: %s\n", msg);
    exit(EXIT_FAILURE);   // 函数内部保证：绝不会 return 回调用者
}

int main(void) {
    if (/* 出错 */ 0) {
        fatal_error("bad input");
    }
    return 0;   // 编译器知道走到这里 fatal_error 不会"掉下来"
}
```

带来的实际好处：

```
调用方视角：
    fatal_error(...)  ──→ 编译器知道这句之后的代码"不可达"
                            → 可以省略后续不必要的寄存器保存/跳转
                            → 若函数体内有路径能"正常返回"，编译器会给出警告
```

`<stdnoreturn.h>` 定义宏 `noreturn`，用法与 `_Noreturn` 相同。标准库里 `exit()`、`abort()`、`longjmp()` 在概念上都是"不返回"的函数（虽然它们的声明方式可能因头文件版本而异）。

**注意**：`_Noreturn` 只是给编译器的一个**承诺**，如果函数实际上还是返回了，是未定义行为，不是说编译器会帮你插入保护代码强制不返回。

### 4.3 `_Generic` —— 泛型选择表达式

```c
#define TYPE_NAME(x) _Generic((x),      \
    int:            "int",              \
    float:          "float",            \
    double:         "double",           \
    char*:          "string",           \
    default:        "unknown")

printf("%s\n", TYPE_NAME(42));      // int
printf("%s\n", TYPE_NAME(3.14));    // double
printf("%s\n", TYPE_NAME("hi"));    // 这里字面量 "hi" 类型是 char[3]，注意和 char* 的区别
```

**底层原理**：`_Generic` 是在**编译期**根据**控制表达式的类型**（不求值该表达式本身，只看类型）在多个分支里选出唯一匹配的一支，其余分支的代码**根本不会被生成**（类似 C++ 里 `if constexpr` 的效果，但 C 没有真正的模板，这是纯粹基于类型的分派）。

```
_Generic( 控制表达式 , 类型1: 表达式1, 类型2: 表达式2, ..., default: 表达式n )
                │
                ▼
      编译器只看"控制表达式"的类型
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
   匹配类型1  匹配类型2  都不匹配→用default
      │         │         │
      ▼         ▼         ▼
   选中表达式1 选中表达式2  选中表达式n
   （其余分支被丢弃，不参与最终生成的代码）
```

**实际用途**：标准库 `<tgmath.h>` 就是靠类似机制（早期靠一堆宏 + 类型判断技巧，C11 之后可以用 `_Generic` 更清晰地实现）做到"一个函数名 `sqrt(x)`，根据 `x` 是 `float`/`double`/`complex` 自动分派到 `sqrtf`/`sqrt`/`csqrt`"。

## 5. 数学函数：`sqrt`、`atan`、`atan2`

均声明在 `<math.h>`，参数与返回值默认是 `double`（`<tgmath.h>` 提供类型通用版本）。

### 5.1 `sqrt`

```c
#include <math.h>
double sqrt(double x);
```

- `x < 0` 时是**定义域错误（domain error）**：返回值是 NaN，并且（在支持 `errno` 的实现中）会设置 `errno = EDOM`。
- 检查方式：

```c
#include <errno.h>
#include <math.h>

errno = 0;
double r = sqrt(-1.0);
if (errno == EDOM) {
    fprintf(stderr, "定义域错误：负数不能开平方\n");
}
```

### 5.2 `atan` vs `atan2` —— 为什么需要两个反正切函数

```c
double atan(double x);              // 返回值范围 (-π/2, π/2)
double atan2(double y, double x);   // 返回值范围 (-π, π]
```

`atan(y/x)` 的根本问题：**丢失了象限信息**。因为 `y/x` 这一个比值，无法区分点在第一象限还是第三象限（符号会互相抵消）。

```
        y
        │
   第二象限 │ 第一象限
  (-,+)  │  (+,+)
 ────────┼──────── x
  (-,-)  │  (+,-)
   第三象限 │ 第四象限
        │

  atan(1/1)   = atan(1) = 45°   （对应第一象限的点 (1,1)）
  atan(-1/-1) = atan(1) = 45°   （但 (-1,-1) 实际在第三象限，应为 225° 或 -135°！）
                                  ← atan 单靠一个比值区分不出来
```

`atan2(y, x)` 把 `y` 和 `x` **分开传入**，函数内部知道两者各自的符号，因此能正确判断点落在哪个象限，返回**真正的角度（弧度）**：

```c
atan2(1.0, 1.0);    //  π/4   (45°，第一象限)
atan2(-1.0, -1.0);  // -3π/4  (-135°，第三象限)   ← 与 atan(1) 明显不同
atan2(1.0, -1.0);   //  3π/4  (135°，第二象限)
atan2(-1.0, 1.0);   // -π/4   (-45°，第四象限)
```

`atan2(0.0, 0.0)` 的具体返回值（是 0 还是未定义）取决于实现/标准附注，我对这一点边界情况的记忆没有十足把握，如果你的代码依赖这个边界值，建议查阅具体平台的 `man atan2` 或标准文本确认。

**实际用途**：从 `(x, y)` 坐标算方向角（游戏开发、机器人朝向、复数的辐角）几乎总是用 `atan2` 而不是 `atan`。

## 6. 程序终止：`exit`、`atexit`

### 6.1 `exit` 与 `return` 的区别

```c
#include <stdlib.h>
void exit(int status);
```

`exit()` 可以在程序**任何位置**调用，立即终止整个程序（不只是终止当前函数），执行流程是：

```
调用 exit(status)
    │
    ▼
1. 按"注册顺序的逆序（LIFO）"依次调用所有通过 atexit() 注册的函数
    │
    ▼
2. 刷新（flush）所有已打开的标准 I/O 流缓冲区，关闭它们
    │
    ▼
3. 将 status 返回给宿主环境（比如 shell 里 echo $?）
    │
    ▼
程序终止
```

而 `main` 里的 `return n;` 在语义上**等价于** `exit(n);`（C99 起标准明确规定，从 `main` 返回等同于调用 `exit`），区别只是写法上一个是"从函数返回"一个是"主动调用退出函数"，最终效果一致。

另有 `_Exit(int status)`（`<stdlib.h>`）：**跳过** `atexit` 注册的清理函数和 stdio 缓冲区刷新，直接终止——类似"强制关机"而不是"正常关机"。

### 6.2 `atexit` —— 注册退出时的清理函数

```c
#include <stdlib.h>
int atexit(void (*func)(void));
```

```c
void cleanup_log(void) {
    printf("关闭日志文件\n");
}

void cleanup_db(void) {
    printf("断开数据库连接\n");
}

int main(void) {
    atexit(cleanup_log);   // 第 1 个注册
    atexit(cleanup_db);    // 第 2 个注册

    printf("程序运行中...\n");
    exit(0);
}
```

**调用顺序是后注册先执行（LIFO，栈式）**：

```
注册顺序：  cleanup_log → cleanup_db
                                  │
exit() 触发时执行顺序：            ▼
                          cleanup_db   （后注册，先执行）
                              │
                              ▼
                          cleanup_log  （先注册，后执行）
```

输出：

```
程序运行中...
断开数据库连接
关闭日志文件
```

C 标准保证**至少可以注册 32 个** `atexit` 函数（具体实现可能支持更多，但不要依赖超出保证值的数量）。这套机制常用于**资源清理**：关闭文件、释放全局资源、打印统计信息等，避免手动在每个 `exit`/`return` 调用点重复写清理代码。

## 7. `assert` 断言机制

```c
#include <assert.h>
void assert(scalar expression);   // 实际上是宏，不是真正的函数
```

```c
int divide(int a, int b) {
    assert(b != 0);   // 断言：调用者保证 b 不为 0
    return a / b;
}
```

**底层机制**：`assert` 本质是一个宏，大致展开为类似（具体措辞因编译器实现而异，这里给的是概念性等价形式，不是标准精确规定的展开文本）：

```c
if (!(b != 0)) {
    fprintf(stderr, "Assertion failed: %s, file %s, line %d\n",
            "b != 0", __FILE__, __LINE__);
    abort();
}
```

可以看到它内部用到了前面提到的 `__FILE__`、`__LINE__` 这两个预定义宏——这就是为什么断言失败信息能精确定位到源码位置（也是 `#line` 能影响这个输出的原因）。

### 关键坑：`NDEBUG` 宏会让 `assert` 彻底消失

```c
#define NDEBUG
#include <assert.h>

assert(some_function_with_side_effect());
// 一旦定义了 NDEBUG，上面这行整体被替换为 ((void)0)
// 也就是说 some_function_with_side_effect() 根本不会被调用！
```

发布构建（Release build）通常会加编译选项 `-DNDEBUG` 来关闭所有断言以提升性能。**这意味着**：

> **绝对不要**把有副作用的、程序逻辑真正需要的代码写在 `assert()` 里面，比如 `assert(x = compute())`——一旦关闭断言，`compute()` 根本不会执行，程序行为在 Debug 和 Release 版本下完全不同。

`assert` 应该只用来表达"这是一个编程错误，不应该发生的前提条件"，不应该用来做正常的错误处理（比如校验用户输入）。

## 8. 内存操作：`memcpy` vs `memmove`

均声明在 `<string.h>`：

```c
void *memcpy(void *restrict dest, const void *restrict src, size_t n);
void *memmove(void *dest, const void *src, size_t n);
```

### 核心区别：能否处理**内存区域重叠**

`memcpy` 的参数带有 `restrict` 限定——这是对编译器/实现的**承诺**：`dest` 和 `src` 指向的内存**绝不重叠**。基于这个承诺，`memcpy` 的典型实现可以**不检查重叠、按最优方式（比如从头到尾、大块搬运、利用 SIMD 指令）复制**，从而获得最高性能。**如果你违反这个承诺（传入重叠区域），是未定义行为。**

`memmove` 没有这个限制，它保证**即使源和目标重叠，结果依然正确**，代价是内部通常需要额外判断方向、必要时用临时缓冲区或反向拷贝，因此**通常比 memcpy 慢一些**。

### 重叠场景图解

假设一个数组，要把 `[2,3,4,5,6]` 往后移 2 位（也就是 `memmove(arr+2, arr, 5*sizeof(int))`）：

```
初始数组:  [1][2][3][4][5][6][7][8]
索引:       0  1  2  3  4  5  6  7

要做的操作: 把 arr[0..4] 拷贝到 arr[2..6]
            src 区间: [0,5)   dest 区间: [2,7)
            → 两个区间在 [2,5) 处重叠！
```

**如果用 `memcpy` 从头到尾正向拷贝**（很多简单实现会这样做），会出现**数据被自己覆盖后又被读取**的错误：

```
第1步: dest[2] = src[0] = arr[0]=1  → arr = [1,2,1,4,5,6,7,8]
第2步: dest[3] = src[1] = arr[1]=2  → arr = [1,2,1,2,5,6,7,8]
第3步: dest[4] = src[2] = arr[2]    ← 但 arr[2] 已经在第1步被改成 1 了！
                                       本该读原来的 3，结果读到了被覆盖后的 1
                                    → arr = [1,2,1,2,1,6,7,8]   ← 数据错误！
```

**`memmove` 会检测到 dest > src 且区间重叠，自动改为从后往前拷贝**，避免"还没读的数据被先写坏"：

```
从后往前:
第1步: dest[6] = src[4] = arr[4]=5  → arr = [1,2,3,4,5,6,5,8]
第2步: dest[5] = src[3] = arr[3]=4  → arr = [1,2,3,4,5,4,5,8]
第3步: dest[4] = src[2] = arr[2]=3  → arr = [1,2,3,4,3,4,5,8]
第4步: dest[3] = src[1] = arr[1]=2  → arr = [1,2,3,2,3,4,5,8]
第5步: dest[2] = src[0] = arr[0]=1  → arr = [1,2,1,2,3,4,5,8]
最终结果正确: [1,2,1,2,3,4,5,8]   ✓ 原来的 2,3,4,5,6 正确整体后移了 2 位
```

**记忆口诀**：确定内存**不重叠**（比如从一个数组拷贝到另一个独立数组）→ 用 `memcpy`（更快）；**不确定是否重叠**，或明确知道**在同一块内存里移动数据**（比如数组内部整体挪位置、`realloc` 后手动调整数据、环形缓冲区操作）→ 用 `memmove`（更安全）。

## 9. 可变参数：`va_start` / `va_arg` / `va_copy` / `va_end`

声明在 `<stdarg.h>`，用于实现像 `printf` 这样"参数个数不固定"的函数。

```c
#include <stdarg.h>

double average(int count, ...) {
    va_list args;
    va_start(args, count);   // count 是"最后一个具名参数"，用它定位可变参数起点

    double sum = 0;
    for (int i = 0; i < count; i++) {
        sum += va_arg(args, int);   // 每次取一个参数，并显式指定其类型
    }

    va_end(args);
    return sum / count;
}

average(3, 10, 20, 30);   // → (10+20+30)/3 = 20.0
```

### 底层原理：函数调用栈上的参数布局

C 函数调用时，参数（在很多常见调用约定下）依次压入调用栈（或部分放入寄存器，具体取决于 ABI，比如 x86-64 System V ABI 会优先用寄存器传递前几个整数/指针参数，浮点数用另一组寄存器，多出的才放栈上）。`va_list` 本质上是对"**当前读取到调用栈/寄存器保存区的哪个位置了**"的一个不透明封装：

```
调用 average(3, 10, 20, 30) 时（概念示意，具体因 ABI 而异）：

栈帧（或寄存器保存区）方向 →
┌────────┬────────┬────────┬────────┐
│ count=3│ 10     │ 20     │ 30     │
└────────┴────────┴────────┴────────┘
    ▲         ▲
    │         │
va_start 之后， args 内部指针指向"count 之后"的位置
    │
    每调用一次 va_arg(args, int)：
        1. 按指定类型(int)从当前位置读出一个值
        2. 内部指针前移一个"参数槽位"的宽度
```

**为什么 `va_arg` 必须显式指定类型？** 因为可变参数部分**没有类型信息保留下来**（不像具名参数在函数原型里写死了类型），全靠调用者（写 `va_arg` 的人）和实际传入的参数类型"心照不宣"地对上——**如果类型不匹配，是未定义行为**，编译器在很多情况下无法帮你检查（这也是 `printf("%d", 3.14)` 这种写反格式化占位符的错误在编译期不一定能被抓出来的根本原因）。

### 关键细节：默认参数提升（default argument promotions）

可变参数部分的实参在传递前会经历"默认参数提升"：

```c
void foo(int fixed, ...) {
    va_list args;
    va_start(args, fixed);

    char c = va_arg(args, char);    // ❌ 错误！不能用 char/short 接收
    // 正确写法：
    int c2 = va_arg(args, int);     // ✓ char/short 类型的实参会被提升为 int
    float f = va_arg(args, float);  // ❌ 错误！
    double d = va_arg(args, double); // ✓ float 类型的实参会被提升为 double

    va_end(args);
}
```

规则：`char`/`short` → 提升为 `int`；`float` → 提升为 `double`。所以 `va_arg` 里**永远不要**写 `char`/`short`/`float`，必须写提升后的类型 `int`/`double`。

### `va_copy` —— 复制一份"读取进度"

```c
void log_msg(const char *fmt, va_list args) {
    va_list args_copy;
    va_copy(args_copy, args);   // 复制一份独立的遍历状态

    vfprintf(stdout, fmt, args_copy);   // 用副本遍历一次（比如打印到屏幕）
    va_end(args_copy);

    vfprintf(logfile, fmt, args);       // 原始的 args 还能再遍历一次（比如写日志）
}
```

**为什么需要 `va_copy`？** 因为 `va_list` 在有些实现里内部是一个**数组类型**（比如 x86-64 System V ABI 下常见实现是一个包含内部状态的结构体数组），直接用 `=` 赋值可能只是拷贝了指针/浅拷贝，导致两份"看起来独立"的 `va_list` 其实共享同一份底层状态，一个遍历完另一个也跟着变了；用 `va_copy` 才能保证标准层面的**正确独立拷贝**。**`va_list` 一旦被 `va_arg` 遍历过，通常不能重新从头开始，除非重新 `va_start`（对原始的可变参数函数）或用 `va_copy` 复制的副本。**

### `va_end` —— 必须配对调用

```c
va_start(args, count);
// ... 使用 args ...
va_end(args);   // 每一次 va_start / va_copy 都必须对应一次 va_end
```

`va_end` 做"清理"工作（具体实现可能什么都不做，也可能需要恢复某些状态）。**忘记调用是未定义行为**，虽然在很多平台上"侥幸能跑"，但不可移植、不安全。

## 10. 内联函数（`inline`，C99 起）

```c
inline int max(int a, int b) {
    return a > b ? a : b;
}
```

### 与宏的对比

```c
#define MAX_MACRO(a, b) ((a) > (b) ? (a) : (b))   // 宏：文本替换，无类型检查，有副作用风险
inline int max_inline(int a, int b) { return a > b ? a : b; }  // 函数：有类型检查，参数只求值一次
```

`inline` 函数解决了宏的两大痛点：**参数只求值一次**（没有 `i++` 被算两次的问题）、**有正常的类型检查**（编译器能捕获类型不匹配的错误）。同时给编译器一个提示：**建议**把函数体直接展开到调用处，省去函数调用的开销（压栈、跳转、返回）——但这只是"建议"，编译器完全可以忽略这个提示（现代编译器很多时候靠自己的启发式判断决定是否内联，`inline` 关键字的实际影响力比很多人以为的要小）。

### C 语言 `inline` 的链接语义（与 C++ 不同，是最容易踩坑的地方）

这是 C 的 `inline` 相比 C++ **最反直觉**的地方：

```c
// 在头文件中：
inline int square(int x) { return x * x; }
```

在 **C99/C11 标准**下，纯粹的 `inline`（没有 `static`/`extern` 修饰）意味着：

> 这个函数体**仅供内联展开使用**，编译器**不保证**会为它生成一份独立可被外部链接调用的函数实体。如果所有调用点都被成功内联展开了，那没问题；但如果编译器在某处选择不内联（比如取了这个函数的地址、或者调用点在其他翻译单元），就需要一个"外部可见的实体"——而纯 `inline` **不提供**这个实体，会导致链接错误。

正确的工程实践通常是二选一：

```c
static inline int square(int x) { return x * x; }
// 每个包含这个头文件的 .c 文件都各自拥有一份"静态"的内联函数副本
// 最安全、最常见的写法，尤其适合写在头文件里
```

或者：

```c
// 头文件.h
inline int square(int x) { return x * x; }

// 恰好一个.c 文件中：
extern int square(int x);   // 这一行"召唤"出一份外部可链接的实体
```

```
static inline 的语义示意：

file_a.c #include "util.h"  ──→ 编译器为 file_a.c 生成自己的一份 square() 副本
file_b.c #include "util.h"  ──→ 编译器为 file_b.c 生成自己的一份 square() 副本
                                （两份互不干扰，链接时不冲突，因为都是 static，
                                 只在各自的翻译单元内可见）
```

**结论**：写跨文件共用的内联工具函数时，最稳妥、最不容易踩坑的写法是 `static inline`。

## 11. C 标准库总览

C 标准库按头文件划分模块，下面是最常用的一批（不同 C 标准版本新增的头文件会有差异，具体某个函数是否在某个平台/版本可用，建议对照实际使用的编译器文档确认）：

| 头文件 | 主要内容 |
|---|---|
| `<stdio.h>` | 标准输入输出：`printf`、`scanf`、`fopen`、`fread`/`fwrite` 等 |
| `<stdlib.h>` | 通用工具：`malloc`/`free`、`exit`/`atexit`、`atoi`/`strtol`、`qsort`、`rand` |
| `<string.h>` | 字符串/内存操作：`strcpy`、`strlen`、`memcpy`、`memmove`、`memset` |
| `<math.h>` | 数学函数：`sqrt`、`pow`、`sin`/`cos`/`atan2`、`floor`/`ceil` |
| `<assert.h>` | `assert` 宏、（C11）`static_assert` |
| `<stdarg.h>` | 可变参数：`va_list`/`va_start`/`va_arg`/`va_copy`/`va_end` |
| `<stdbool.h>` | `bool`/`true`/`false` 宏（底层仍是 `_Bool`，C23 起 `bool` 可能成为真正关键字，具体请以对应标准文本为准） |
| `<stdint.h>` | 定宽整数类型：`int32_t`、`uint64_t` 等，配套 `<inttypes.h>` 做格式化 |
| `<time.h>` | 时间/日期：`time`、`clock`、`strftime` |
| `<ctype.h>` | 字符分类/转换：`isalpha`、`isdigit`、`toupper` |
| `<errno.h>` | 错误码：`errno`、`EDOM`、`ERANGE` |
| `<limits.h>` / `<float.h>` | 整数/浮点类型的取值范围常量 |
| `<stdnoreturn.h>` | `noreturn` 宏（C11，对应 `_Noreturn`） |
| `<tgmath.h>` | 类型通用数学函数（基于 `_Generic` 思想，自动分派 `float`/`double`/复数版本） |

### 学习建议（不是标准内容，是个人经验性建议，供参考）

- 遇到不确定某个函数的**边界行为**（比如参数为 0、负数、NULL 时怎么样）时，**优先查 man 手册（Linux: `man 3 函数名`）或 cppreference.com**，不要凭印象猜测，尤其是 `errno` 设置规则、返回值语义这类细节在不同函数间差异很大。
- 涉及**未定义行为（UB）**的地方（比如宏参数副作用、内存重叠、`va_arg` 类型不匹配）要格外小心：UB 的可怕之处在于"当前编译器/优化等级下侥幸能跑"，换个编译器或开更高优化就可能崩溃或产生诡异结果。
