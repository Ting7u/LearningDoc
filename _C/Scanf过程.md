# scanf 从输入到输出：完整流程详解

本文档整理了 `scanf("%d", &age)` 这一行代码执行时，数据从键盘到变量所经历的**完整路径**——涵盖硬件、操作系统、C 标准库、以及 scanf 自身的解析逻辑四个层次。

---

## 一、整体流程图

```
┌─────────────────────────────────────────────────────────────┐
│ 第1层：硬件                                                    │
│   你按下键盘上的某个键（比如 'A'）                               │
│   → 键盘发送一个"扫描码"(scancode) 给主板                       │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第2层：操作系统内核 —— 键盘驱动 + tty(终端)子系统                 │
│   内核把扫描码翻译成字符 'A'                                     │
│   放进内核里的一块"终端输入缓冲区"(tty line buffer)               │
│   在"行缓冲模式(canonical mode)"下，这块缓冲区会一直攒着，         │
│   直到你按下回车键才标记为"整行可读"                              │
└─────────────────────────────────────────────────────────────┘
                          │  按下回车，内核把这一整行标记为"可读"
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第3层：系统调用边界 —— read()                                   │
│   程序调用 read()，请求内核"把可读数据拷贝给我"                   │
│   内核把数据从"内核空间"拷贝到"用户空间"（你的程序内存里）          │
│   如果此时内核还没有数据 → 见下文"进程阻塞与调度"                  │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第4层：C标准库(libc) —— stdio 内部缓冲区                        │
│   数据被拷贝进 FILE* stdin 结构体内部维护的一块内存缓冲区          │
│   （通常几KB大小，属于用户态，即你的程序自己的内存）               │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第5层：getchar() / fgetc()                                    │
│   每次调用先看 stdio 缓冲区里还有没有数据：                       │
│     有 → 直接从缓冲区取一个字符，立即返回（不阻塞）                │
│     没有 → 触发 read() 系统调用，向内核再要一批数据补满缓冲区      │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第6层：scanf 的解析引擎                                         │
│   反复调用 getchar()，一个字符一个字符地"看"                     │
│   判断：这是空白？是数字？该不该停？该不该退回去(ungetc)？         │
│   按格式串(%d %s...)把看到的字符序列做"类型转换"                  │
│   （字符序列 "123" → 整数 123）                                 │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────┐
│ 第7层：写回调用者的变量                                          │
│   scanf 拿到调用者传入的指针（比如 &age）                        │
│   把转换好的值直接写到指针指向的内存里                            │
│   （这块内存和 stdio 缓冲区是完全不同的两块内存）                  │
└─────────────────────────────────────────────────────────────┘
```

**核心原则：每一层只管自己这一层的事，靠下一层把"脏活"做完。**
`scanf` 的作者写解析逻辑时，完全不用操心键盘和内核，只需要在 `getchar()` 返回的字符流上做文章。

## 二、"程序卡住等输入"背后发生了什么——进程阻塞与调度

很多人以为 `getchar()` 自己在"循环等待"，但实际上：

> **不是 `getchar()` 在"等"，而是操作系统把整个进程挂起了，一条指令都不执行。**

### 完整过程

1. **`getchar()` 发现 stdio 缓冲区是空的**，于是调用 `read()`（系统调用，从用户态陷入内核态）。
2. **内核检查终端设备**：现在有数据可读吗？如果你还没按键，答案是"没有"。
3. **内核不会傻等**（那样会浪费 CPU），而是：
   - 把进程状态从 `Running`（运行中）标记为 `Blocked`（阻塞/睡眠）
   - 把该进程从 CPU 上摘下来，CPU 转去执行别的进程
   - 在这个终端设备上挂一个"等待列表"，把该进程放进去
4. **你按下键盘** → 硬件中断 → 内核键盘驱动被唤醒 → 字符被放进 tty 缓冲区。
5. **内核检查等待列表**，发现刚才是你的进程在等，于是把它的状态从 `Blocked` 改回 `Runnable`（可运行），扔回调度队列。
6. **等 CPU 调度器选中你的进程**，`read()` 才真正返回，数据被拷贝进 stdio 缓冲区，`getchar()` 从中取出字符，程序才第一次真正"继续往下走"。

### 状态图

```
程序调用 getchar()
        │
        ▼
   缓冲区有数据吗？
    │           │
   有          没有
    │           │
返回字符      调用 read()（系统调用，陷入内核）
（不阻塞）        │
              内核态没有数据可读
                    │
                    ▼
        进程状态: Running → Blocked
        （从CPU上被摘下，一条指令都不执行）
                    │
             （你按下键盘……）
                    │
                    ▼
              内核把数据放进tty缓冲区
              唤醒进程: Blocked → Runnable
                    │
             （等CPU调度器选中它）
                    │
                    ▼
        进程状态: Runnable → Running
        read() 系统调用返回，拷贝数据
        getchar() 从缓冲区取字符，返回
                    │
                    ▼
           程序继续往下执行
```

## 三、已经手写验证过的底层积木

以下代码均已实际编译、运行、验证过输出正确。

### 3.1 读一个字符——为什么类型必须是 `int` 而不是 `char`

```c
int c;  /* 注意：不是 char */
c = getchar();
```

**原因**：`getchar()` 的返回值需要同时表示两种东西——
- 一个正常字符（取值范围 0~255）
- 特殊标记 `EOF`（通常值为 -1，代表"输入结束"）

如果 `c` 声明成 `char`，在很多系统上 `char` 默认是无符号类型，取值范围只有 0~255，**根本装不下 -1**，会导致"输入结束"这个信号丢失或被错误识别成某个具体字符。这是新手写 C 时最容易踩的经典陷阱。

**验证结果**：输入 `"abc"`，程序只读了第一个字符 `'a'`（ASCII 值 97），`%c` 和 `%d` 两种格式打印同一个 `c`，证明"字符在计算机里本质上就是一个数字"。

### 3.2 预读 + 退回机制（`inchar` / `ungetc`）

scanf 经常要"读了一个字符之后才知道它算不算数"。比如解析 `%d` 读 `"123abc"`：读到 `a` 才发现该停了，但 `a` 已经被拿出来了，必须"还回去"，留给后面的逻辑处理。

```c
static int my_inchar(FILE *stream, long *read_count)
{
    int c = getchar_unlocked();
    (void)stream;
    if (c != EOF)
        (*read_count)++;
    return c;
}

static void my_ungetc(int c, long *read_count)
{
    if (c == EOF)
        return; /* EOF 不是"真正读到的字符"，不需要也不能退回 */
    (*read_count)--;
    ungetc(c, stdin);
}
```

**关键细节**：
- 用 `_unlocked` 版本跳过每次调用都要加锁/解锁的开销（真实 glibc 在外层一次性加锁，内部循环全程用免锁版本读字符）。
- `read_count` 对应 glibc 源码里的 `read_in` 变量——这是 `%n` 转换符存在的全部理由：`%n` 不读任何输入，只是把"已读字符总数"写回调用者。
- `if (c == EOF) return;` 这个判断容易被忽略，但漏掉会导致计数错乱或未定义行为。

**验证结果**：连续读 3 个字符 `a b c`，退回第 3 个字符后计数从 3 变回 2，再读一次又拿回 `c`，计数恢复到 3——证明退回机制和计数器完全同步。

### 3.3 跳过空白字符

`scanf("%d", &age)` 遇到输入 `"   123"`（前面带空格）时，不应该因为第一个字符是空格就报错，而要先跳过空白再找数字。

```c
static void skip_whitespace(void)
{
    int c;

    while ((c = getchar()) != EOF && isspace(c)) {
        /* 什么都不做，只是把空白字符"吃掉"，不保留 */
    }

    /* c 要么是 EOF，要么是第一个"非空白"字符，
     * 无论哪种，都不属于空白，必须退回去。*/
    if (c != EOF)
        ungetc(c, stdin);
}
```

**关键细节**：
- `c != EOF` 必须写在 `isspace(c)` **前面**，利用 `&&` 短路求值：一旦 `c == EOF`，`isspace(c)` 根本不会被执行——因为 `isspace` 接受负数（EOF 通常是 -1）之外的值才是良定义行为。
- `isspace()` 认的"空白"不止空格，还包括 `\t`、`\n`、`\r`、`\v`、`\f`。

**验证结果**：分别测试纯空格 `"   X"` 和混合空白 `"\t\n  Y"`，两种情况都能准确跳过所有空白，拿到后面的非空白字符。

## 四、对应回 glibc 真实源码

我们手写的这几个积木，在 glibc 的 `stdio-common/vfscanf-internal.c` 里都能找到对应：

| 我们写的 | glibc 里的对应物 | glibc 多做的事 |
|---|---|---|
| `my_inchar` | 宏 `inchar()` | 额外记录 `errno`，区分"正常EOF"和"读取时系统错误" |
| `my_ungetc` | 宏 `ungetc(c, s)` | 逻辑完全一致 |
| `skip_whitespace` | 数字/浮点数等转换开始前的 `do { ... } while (ISSPACE(c))` 段 | 额外保存/恢复 `errno`；并根据转换符类型（`%c`、`%[`、`%n` 不跳空白）决定要不要执行这一步 |

**核心结论**：glibc 代码之所以显得庞大难读，不是因为核心逻辑复杂，而是因为它在我们这个"教学骨架"之上，叠加了：
- 完整的错误处理（区分多种失败原因）
- 宽字符/窄字符两套实现共用一份源码（通过宏区分）
- 本地化（locale）支持
- 动态内存分配（`%m` 标志）
- 每个转换符各自的具体细节（字段宽度、进制前缀、千位分隔符等）
