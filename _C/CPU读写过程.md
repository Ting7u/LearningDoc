# CPU 读取内存的完整流程

## 一、核心结论先说

CPU 和内存之间**不是**按"你要几个字节就搬几个字节"来工作的。无论你只想读 1 个字节,还是 8 个字节,硬件底层都会**先搬回一整块**(通常是一条 cache line,常见 64 字节),再从这一整块里"挑"出你真正要的那部分。这也是为什么——**只要落在同一个对齐块内,读 1 字节和读 8 字节,耗时基本一样**;真正拉开差距的是"要发起几次这样的搬运操作"。

---

## 二、内存的物理组织:按"块"存在,不是按"字节"存在

把内存想象成一排排**固定宽度的抽屉**,64 位系统里,总线搬运的最小单位常见是一条 **cache line(缓存行,通常 64 字节)**:

```
抽屉0            抽屉1            抽屉2
0x1000~0x103F   0x1040~0x107F   0x1080~0x10BF
[==== 64B ====] [==== 64B ====] [==== 64B ====]
```

CPU 发出的访存指令(不管是 `movb` 读1字节,还是 `movq` 读8字节),最终都要落到"访问某个抽屉"这个动作上。

---

## 三、完整读取流程(以读 1 个字节为例)

假设要执行 `movb (0x1003), %al`(读地址 `0x1003` 这 1 个字节),这个地址落在"抽屉0"(`0x1000~0x103F`)里。

```
第1步: CPU 发出地址 0x1003

第2步: 检查 L1 Cache 里有没有这条 cache line
        ├─ 命中(Hit)  → 直接从 cache 里取,几个时钟周期,很快
        └─ 未命中(Miss)→ 要往下一级(L2 → L3 → 主存)逐级去要,慢很多

第3步: 假设 Miss,发起一次内存事务,把整条 cache line(64字节)搬进 L1 Cache
        [0x1000][0x1001][0x1002][0x1003][0x1004]...[0x103F]
                                   ↑
                            这才是你真正想要的字节

第4步: CPU 内部用"字节选择电路"(数据选择器/移位器),
        从这 64 字节里精确挑出第 4 个字节(0x1003)

第5步: 把挑出来的这 1 字节,放进目标寄存器 %al
```

**图示总结:**

```
内存 (主存/下级缓存)
┌─────────────────────────────────────┐
│ 0x1000 ~ 0x103F (完整一条cache line)  │  ← 整块被搬走
└─────────────────┬─────────────────────┘
                   │ 总线搬运(一次事务)
                   ▼
┌─────────────────────────────────────┐
│      L1 Cache (CPU内部高速缓存)        │  ← 副本存在这里
└─────────────────┬─────────────────────┘
                   │ 字节选择电路(挑选/移位)
                   ▼
              [0x1003的值]
                   │
                   ▼
              目标寄存器 %al
```

## 四、写入更复杂:读-改-写(Read-Modify-Write)

读取只需要"挑",但写入不能只对内存"戳"进去 1 个字节——总线只能整块整块地往内存里拍数据。所以写 1 个字节,真实流程是:

```
目标: 把地址 0x1003 这 1 字节改成新值 0xAB

第1步: 先把整条 cache line(0x1000~0x103F)读到 L1 Cache
        [原值][原值][原值][原值][原值]...[原值]

第2步: 在 Cache 内部,只把 0x1003 对应的那 1 个字节替换成新值
        [原值][原值][原值][ 0xAB ][原值]...[原值]
                              ↑ 只有这里变了

第3步: 这条 cache line 被标记为"脏"(dirty),
        之后某个时机(被换出/主动flush)整块写回主存
```

这也解释了**为什么未对齐访问的"写"操作更慢**——如果你要写的数据横跨两条 cache line,上面这套"读-改-写"流程要对**两条 line 各走一遍**,开销直接翻倍。

---

## 五、为什么"读1字节"和"读8字节"耗时差不多

关键认知:**耗时的大头,在"发起并完成一次访存事务"这件事本身**(尤其是 cache miss、要走总线去内存要数据的时候),不在于"这次事务里具体挑了几个字节"。

```
情况A: 读 1 字节(0x1003)          情况B: 读 8 字节(0x1008~0x100F,已对齐)
─────────────────────────         ─────────────────────────
① 查cache → miss                  ① 查cache → miss
② 发起1次内存事务,搬64字节         ② 发起1次内存事务,搬64字节 (同一条line)
③ 挑出其中1个字节                  ③ 挑出其中连续8个字节
─────────────────────────         ─────────────────────────
耗时 ≈ T                           耗时 ≈ T   (基本相同!)
```

"挑1个字节"和"挑连续8个字节",在硬件电路里是**同一级组合逻辑、单周期完成**的并行操作,不会因为多挑几个字节就线性变慢。两种情况真正的大头开销——"有没有命中cache""要不要走总线搬一整块"——是完全一样的。

---

## 六、真正的性能差异体现在"次数",不是"单次快慢"

拿 `memset` 清零 64 字节内存举例:

```
方案A: 用 byte* 逐字节写,循环64次
        每次都是"1次访存事务级别的开销" × 64
        总耗时 ≈ 64 × T

方案B: 用 op_t*(8字节)每次写8字节,循环8次
        每次访存事务开销和方案A的单次开销基本相同,约为T
        总耗时 ≈ 8 × T
```

方案B 总耗时约为方案A的 **1/8**——不是因为"一次写8字节"比"一次写1字节"更快,而是因为完成同样的总任务,**方案B 只需要发起 8 次访存/循环操作,而方案A 需要发起 64 次**。省下来的是"重复发起操作、循环判断、指令译码"这些每次都要付出的固定开销。

这正是 glibc `memset` 宁可多花几行代码做地址对齐、也要尽量用 `op_t`(甚至一次 8 个 `op_t` 即 64 字节)去批量写的原因——用更少的"事务次数",干掉原本需要更多次"事务"才能完成的活。

---

## 七、地址对齐为什么重要:避免"跨块"

如果起始地址没有对齐到 `op_t` 的边界(比如从 `0x1003` 开始做 8 字节整存取),这 8 字节会**横跨两条抽屉**:

```
抽屉0: 0x1000 0x1001 0x1002 [0x1003 0x1004 0x1005 0x1006 0x1007]
抽屉1: [0x1008 0x1009 0x100A] 0x100B ...
        ↑-- 你要的8字节,横跨了两条cache line/两个抽屉 --↑
```

这种"未对齐访问"会导致:

- **部分架构(老ARM、MIPS等)直接不支持,触发硬件异常、程序崩溃**
- **x86等虽支持,但要拆成两次总线访问 + 一次数据拼接,慢不止一倍**

而对齐后的访问,永远只落在一条抽屉/一条cache line内,一次事务就能搞定,又快又安全。

## 八、全流程一张总图

```
                 CPU 想读/写某个地址
                        │
                        ▼
              地址是否已在 L1 Cache?
              ┌─────────┴─────────┐
             是(Hit)             否(Miss)
              │                    │
              │           向下一级(L2→L3→主存)
              │           搬回整条 cache line(如64B)
              │                    │
              └─────────┬──────────┘
                        ▼
          在 Cache 内,用字节选择电路
          从这一整块里"挑"出/"替换"目标字节
                        │
              ┌─────────┴─────────┐
             读                   写
              │                    │
        送入目标寄存器      cache line标记为dirty,
                            之后整块写回主存
```

---

## 九、一句话总结

- 内存搬运的最小单位是"一整块"(cache line,常见64字节),不是按你要的字节数来搬。
- 读1字节和读8字节(只要都在同一对齐块内),耗时基本相同,因为瓶颈在"发起一次访存事务",不在"挑几个字节"。
- 写操作比读复杂,要走"读-改-写"流程,因为总线只能整块写回内存。
- 未对齐访问会导致"跨块",轻则变慢(拆成两次事务+拼接),重则直接崩溃。
- 性能优化(如 `memset` 用大块 `op_t` 写)的真正收益,来自**减少访存事务/循环的总次数**,而不是让单次操作本身变快。
