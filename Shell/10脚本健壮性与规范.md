# 第 10 章　脚本健壮性与规范

## 本章目标

- 理解 Shell 脚本"默认出错继续跑"的危险，会用 `set -e`、`set -u`、`set -o pipefail`，并知道它们的坑
- 会做错误处理、日志输出、临时文件管理（`mktemp`）
- 会用 ShellCheck 做静态检查，会用 `bash -n`、`set -x` 调试
- 分清 bash 特性与 POSIX sh，知道 GNU 与 BSD 工具的常见差异
- 建立安全意识：引号、`--`、命令注入、临时文件、敏感信息

> 前面几章教你"怎么写出能跑的脚本"，这一章教你"怎么写出出了问题也不会闯祸的脚本"。

---

## 10.1 为什么需要健壮性

Shell 默认的行为是：**某条命令失败了，继续执行下一条**。

```bash
#!/usr/bin/env bash
cd /some/build/dir          # 目录不存在，cd 失败了
rm -rf ./*                  # 但脚本继续往下跑：删除的是"当前所在目录"里的所有东西！
```

这类问题的根源只有几类：命令失败没人发现、变量没设置却被当作空串、管道里前面的命令失败被忽略、没有清理现场。本章的内容就是逐个堵住这些口子。

---

## 10.2 严格模式：`set -e`、`set -u`、`set -o pipefail`

脚本开头常见的一行：

```bash
#!/usr/bin/env bash
set -euo pipefail
```

分别看这三个选项。

### `set -e`（errexit）：命令失败就退出

```bash
set -e
echo "开始"
false                       # 返回非 0，脚本立刻退出
echo "这一行不会执行"
```

看起来很美好，但 `set -e` 有一大堆**例外**，不了解它们就会误以为"有 `set -e` 就安全了"：

**1. 条件上下文中的失败不会触发退出**

`if`/`while`/`until` 的条件、`!` 取反的命令、`&&` 和 `||` 链中**除最后一个以外**的命令，失败都不会触发退出：

```bash
set -e
if false; then echo x; fi           # 不退出
false || echo "处理失败"             # 不退出
false && echo "不会打印"             # 不退出（false 在 && 的左边）
echo "仍在运行"
```

**2. 函数在条件上下文里被调用时，函数内部的 `set -e` 实际上失效了**

```bash
set -e
f() {
    false
    echo "f 里 false 之后的这行仍然会执行"
}
if f; then echo "f 成功"; fi        # f 在 if 条件里：函数内部的失败不会让脚本退出
```

这是最反直觉的一条：你以为函数里第一个失败的命令会中止函数，实际上不会。

**3. 管道只看最后一个命令的状态**（除非开启 `pipefail`）

```bash
set -e
false | cat                         # 整条管道的状态是 cat 的（0），不退出
echo "仍在运行"
```

**4. `local x=$(cmd)`、`export x=$(cmd)` 会吞掉 `cmd` 的失败**（第 7 章讲过）：

```bash
set -e
f() {
    local out=$(false)              # 状态是 local 的（0），不会退出
    echo "还在运行"
}
f
```

正确写法是分开：`local out; out=$(cmd)`。

**5. `(( ))` 的算术结果为 0 时返回状态 1**（第 5 章讲过）：

```bash
set -e
i=0
((i++))                             # 表达式的值是旧值 0 → 状态 1 → 脚本退出！
echo "到不了这里"
```

写成 `i=$((i + 1))` 就没有这个问题；或者 `((i++)) || true`。

**6. 想"允许失败"时要明确写出来**：

```bash
set -e
grep -q "foo" file.txt || true      # grep 没找到会返回 1，用 || true 明确表示"没找到没关系"
```

另一个经常遇到的情形：脚本（或函数）的最后一条命令是 `[ -f x ] && echo yes`，条件为假时整个脚本的退出状态是 1。

> **关于 `set -e` 的态度**：由于上面这些例外，而且细节在不同 bash 版本和不同 Shell 之间还有差异，
> 许多有经验的脚本作者对它持保留态度：它能在简单脚本里兜底，但**不能当作完整的错误处理方案**。
> 比较务实的做法是：开启它作为"安全网"，同时对关键命令仍然**显式检查**（见 10.3）。

### `set -u`（nounset）：使用未设置的变量就报错

```bash
set -u
echo "$undefined_var"               # bash: undefined_var: unbound variable
```

它能抓住变量名拼写错误，也能防止第 2 章提到的 `rm -rf "$DIR/"` 在 `DIR` 为空时变成 `rm -rf /`。

需要"允许变量可能未设置"时，给默认值：

```bash
set -u
name="${1:-}"                       # $1 没有传时得到空串，不报错
[ -n "${DEBUG:-}" ] && echo "debug on"
```

两个坑：

- `$@`、`$*` 在没有参数时是安全的，但**空数组**在较老的 bash（4.3 及更早，包括 macOS 自带的 3.2）里，`"${arr[@]}"` 会触发 `unbound variable`。bash 4.4 起修复了。
- 检查变量是否设置，用 `${var+x}` 或 `${var:-}`，而不是直接 `[ -n "$var" ]`。

### `set -o pipefail`：管道里任何一个命令失败，整条管道就算失败

```bash
false | true;  echo $?              # 0（默认只看最后一个）
set -o pipefail
false | true;  echo $?              # 1（取最后一个非 0 的状态）
```

坑：**SIGPIPE**。当右边的命令提前退出（比如 `head -n 1` 读完第一行就退出），左边的命令继续写入会收到 `SIGPIPE`，退出状态是 `141`（128 + 13），在 `pipefail` 下整条管道就算"失败"：

```bash
set -o pipefail
yes | head -n 1                     # 输出 y，但管道状态是 141
echo $?
```

如果同时开着 `set -e`，脚本就会在这里退出。另一个常见的类似问题：`cmd | grep -q pattern` 中 `grep -q` 一旦匹配就退出，左边的 `cmd` 可能因 SIGPIPE 而"失败"。

还有一个：`some_cmd | grep pattern` 在**没有匹配**时 `grep` 返回 1，配合 `set -e` 会让脚本退出。要容忍的话：`some_cmd | grep pattern || true`。

> `pipefail` 不是所有 Shell 都支持。写 `#!/bin/sh` 的脚本之前，要在目标 Shell 上实际测试。

### 在特定位置临时关闭

```bash
set +e
risky_command
rc=$?
set -e
echo "risky_command 的状态: $rc"
```

更简洁的写法是直接捕获状态：

```bash
rc=0
risky_command || rc=$?
```

## 10.3 错误处理

### 显式检查 + `die`

```bash
die() {
    printf 'error: %s\n' "$*" >&2
    exit 1
}

cd "$dir" || die "无法进入目录: $dir"
[ -r "$file" ] || die "文件不可读: $file"
command -v curl >/dev/null 2>&1 || die "需要安装 curl"
```

要点：

- 错误信息输出到 **stderr**（`>&2`，第 3 章）
- 用有意义的**退出状态码**（第 7 章：1 一般错误，2 用法错误）
- 检查依赖用 `command -v 命令`（比 `which` 更可移植）

### `trap ERR`：出错时报告位置（bash 特性）

```bash
set -Eeuo pipefail
trap 'echo "第 $LINENO 行出错: $BASH_COMMAND (状态 $?)" >&2' ERR
```

- `LINENO` 是出错的行号，`BASH_COMMAND` 是失败的命令
- `set -E`（errtrace）让函数、命令替换里的错误也能触发 `ERR` 陷阱
- `ERR` 陷阱的触发条件和 `set -e` 基本一致，所以前面那些例外同样适用

### `trap EXIT`：无论怎么退出都清理

第 8 章讲过。关键点：`EXIT` 陷阱里的 `$?` 是脚本即将返回的状态，陷阱执行完后脚本仍然以**原来的状态**退出（除非陷阱自己调用了 `exit`）：

```bash
cleanup() { rm -f -- "$tmpfile"; }
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
```

### 重试函数

```bash
retry() {
    local tries=$1 delay=$2 i
    shift 2
    for ((i = 1; i <= tries; i++)); do
        if "$@"; then
            return 0
        fi
        echo "第 $i/$tries 次失败: $*" >&2
        sleep "$delay"
    done
    return 1
}

retry 3 2 curl -fsS -o /dev/null https://example.com || die "重试 3 次仍失败"
```

`"$@"` 把传进来的整条命令原样执行（第 7 章）。

## 10.4 日志输出

### 用 `printf` 代替 `echo`

`echo` 的行为在不同 Shell 间不一致（`-e`、`-n` 的处理、转义序列），而且当内容恰好是 `-n` 之类时会被当成选项：

```bash
x="-n"
echo "$x"                           # bash 中什么也不输出（被当成了选项）
printf '%s\n' "$x"                  # 输出 -n
```

规则：**输出变量的内容时用 `printf '%s\n' "$var"`**。

### 简单的日志函数

```bash
log()   { printf '%s [%s] %s\n' "$(date '+%F %T')" "$1" "${*:2}" >&2; }
info()  { log INFO  "$@"; }
warn()  { log WARN  "$@"; }
error() { log ERROR "$@"; }

info "开始备份"
warn "磁盘剩余空间不足"
```

输出类似：

```
2026-11-26 10:00:01 [INFO] 开始备份
```

`${*:2}` 是"从第 2 个参数开始的所有参数"（第 5 章的子串展开用在位置参数上）。

### 把脚本的全部输出写入日志文件

```bash
LOG="$HOME/backup.log"
exec >>"$LOG" 2>&1                  # 从这一行起，脚本的 stdout 和 stderr 都追加到日志
echo "之后的输出都会进日志"
```

`exec` 不带命令，只做重定向，对整个脚本生效。想既写文件又显示在屏幕上，需要 `tee` 配合进程替换，第 11 章会讲。

## 10.5 临时文件：`mktemp`

```bash
tmpfile=$(mktemp)                   # 创建一个唯一命名的临时文件，输出它的路径
tmpdir=$(mktemp -d)                 # 创建一个临时目录
```

指定名字模板（末尾的 `XXXXXX` 会被随机字符替换）：

```bash
tmpfile=$(mktemp "${TMPDIR:-/tmp}/myscript.XXXXXX")
```

为什么不用 `/tmp/myscript.$$` 这类固定名字：

- 名字可预测：攻击者可以提前在 `/tmp` 里创建同名文件或符号链接，让你的脚本去写别的地方
- `mktemp` 保证文件是**新创建**的，并且权限是 `600`（目录是 `700`），只有你自己能读写

配合 `trap` 清理：

```bash
tmpdir=$(mktemp -d) || exit 1
trap 'rm -rf -- "$tmpdir"' EXIT
```

> 可移植性：不带参数的 `mktemp` 在不同系统上行为不完全一致，带模板的写法（`mktemp "${TMPDIR:-/tmp}/name.XXXXXX"`）是比较稳妥的做法。
> macOS 的 `mktemp -t 前缀` 与 GNU 的 `-t` 含义也不同，遇到时以本机 `man mktemp` 为准。

## 10.6 ShellCheck：静态检查

**ShellCheck** 是 Shell 脚本的静态分析工具，能在运行前发现大量引号、可移植性、逻辑方面的问题。强烈建议所有脚本都跑一遍。

安装方式因系统而异（多数包管理器里都有），具体命令请以 ShellCheck 官方说明为准。

```bash
shellcheck script.sh
shellcheck -s bash script.sh        # 指定方言（没有 shebang 时有用）
```

看一个有问题的脚本：

```bash
#!/bin/bash
files=$(ls *.txt)
for f in $files; do
    cd $dir
    content=$(cat $f)
    echo $content
done
read name
```

ShellCheck 会针对这些写法给出警告，常见的编号（按我的了解）有：

| 编号 | 含义 |
|------|------|
| SC2086 | 变量没加双引号，可能发生单词拆分和通配符展开 |
| SC2046 | 命令替换没加双引号 |
| SC2164 | `cd` 之后没有处理失败：用 `cd ... \|\| exit` |
| SC2155 | `local x=$(cmd)` 会掩盖 `cmd` 的退出状态，应拆成两行 |
| SC2162 | `read` 没有加 `-r` |
| SC2012 | 解析 `ls` 的输出不可靠，应该用 glob 或 `find` |
| SC2034 | 变量赋值了但从未使用 |

> 编号和措辞可能随版本调整，以你本机 `shellcheck` 的实际输出为准。

对确实不想修改的地方，可以用注释关闭某条规则，并**写明理由**：

```bash
# shellcheck disable=SC2086   # 这里需要单词拆分，$opts 是多个选项
cmd $opts "$file"
```

在 `Makefile` 或 CI 里运行 ShellCheck（见第 12 章），可以让问题在合并前就被发现。

## 10.7 调试

### 只检查语法，不执行

```bash
bash -n script.sh                   # 语法有问题会报错；不会运行任何命令
```

### 跟踪执行：`bash -x` 与 `set -x`

```bash
bash -x script.sh                   # 打印每条命令（展开后的样子），前面带 +
```

在脚本内部局部开启：

```bash
set -x
some_function
set +x
```

输出类似：

```
+ some_function
+ echo hello
hello
```

每多一层嵌套（函数、子 Shell），前面的 `+` 多一个。

### 自定义 `PS4`：让跟踪信息带上文件名和行号

```bash
PS4='+ ${BASH_SOURCE[0]##*/}:${LINENO}: '     # 单引号：每次打印跟踪信息时才展开
set -x
some_function
```

输出类似 `+ script.sh:4: some_function`。

> 这里要写在**脚本里面**。我在 bash 5.2 上测试过：在命令行用环境变量传入（`export PS4=...; bash -x script.sh`）没有生效，
> 跟踪输出仍然是默认的 `+ `。原因我没有深究，所以不要依赖环境变量传 `PS4`。

### 跟踪信息单独写到文件

```bash
bash -x script.sh 2> trace.log      # stderr 里的跟踪信息写入文件
```

⚠️ **`set -x` 会把展开后的命令（包括密码、令牌）打印出来**。处理敏感信息的地方要先 `set +x`，CI 日志里尤其要小心。

### 其他实用技巧

- 打印变量时用方括号包起来，空白和空值一目了然：`echo "DEBUG: x=[$x]" >&2`
- 把脚本拆成小函数，在函数里逐个测试
- 用 `declare -p 变量名` 查看变量的完整内容和属性（数组特别有用）

## 10.8 可移植性：bash 与 POSIX sh

### 先决定目标

| 目标 | 做法 |
|------|------|
| 只在 bash 上跑 | shebang 写 `#!/usr/bin/env bash`，放心用 bash 特性（但要写明最低版本） |
| 要在 `sh`（如 dash、busybox ash）上跑 | shebang 写 `#!/bin/sh`，**只用 POSIX 特性**，并用 `dash` 之类实际测试 |

不要写 `#!/bin/sh` 却用了 bash 特性：在 `/bin/sh` 指向 dash 的系统（如 Debian/Ubuntu）上会出错。

### 常见 bash 特性与 POSIX 写法对照

| bash 特性 | POSIX sh 的写法 |
|-----------|-----------------|
| `[[ $a == x* ]]` | `case $a in x*) ... ;; esac` |
| `[[ -f $f && -r $f ]]` | `[ -f "$f" ] && [ -r "$f" ]` |
| `[ "$a" == "$b" ]` | `[ "$a" = "$b" ]` |
| `[[ $s =~ regex ]]` | `echo "$s" \| grep -E regex`，或 `case` |
| `arr=(a b c)` 数组 | 用位置参数 `set -- a b c`，或换行分隔的字符串 |
| `echo -e "a\tb"`、`echo -n` | `printf 'a\tb\n'` |
| `source file` | `. file` |
| `function f { ...; }` | `f() { ...; }` |
| `{1..5}` | `seq 1 5`（非 POSIX 但常见），或 `while` 循环 |
| `(( i++ ))`、`for ((...))` | `i=$((i + 1))`，`while` 循环 |
| `${var//a/b}`、`${var:2:3}`、`${var^^}` | 用 `sed`、`cut`、`tr` 等外部命令，或 `${var#...}`/`${var%...}` |
| `<<< "str"` | `echo "str" \| cmd`，或 here document |
| `&>`、`\|&` | `> file 2>&1`、`2>&1 \|` |
| `read -p "提示" x` | `printf '提示'; read -r x` |
| `$RANDOM`、`$BASHPID` | 没有可移植的等价物 |
| `local` | 不在 POSIX 标准里，但 dash、bash、zsh、busybox ash 都支持，实践中通常可用 |
| `<(cmd)` 进程替换 | 用临时文件或命名管道 |

用 `dash` 快速检查脚本是否真的只用了 POSIX 特性：

```bash
dash -n script.sh                   # 语法检查
dash script.sh                      # 实际运行
```

### GNU 工具与 BSD 工具的差异

Linux 上是 GNU 版本，macOS 上是 BSD 版本，下面这些最常见：

| 命令 | 差异 |
|------|------|
| `sed -i` | GNU：`sed -i 's/a/b/' f`；BSD 要求 `-i` 后面带备份后缀参数。写 `sed -i.bak` 两边通常都可用 |
| `date -d "yesterday"` | GNU 专有；BSD 用 `date -v-1d` |
| `grep -P` | 不是所有平台都支持 |
| `xargs -r` | GNU 专有（空输入时不执行） |
| `stat -c '%a'` | GNU；BSD 用 `stat -f '%Lp'` |
| `find -printf` | GNU 专有 |
| `sort -h` | 较老的 BSD sort 可能没有 |

做法：**在脚本开头的注释里写明依赖**（"需要 GNU sed"、"需要 bash ≥ 4.3"），必要时在脚本里检测并给出明确的报错。

## 10.9 安全意识

### 1. 变量一律加引号，选项结束用 `--`

```bash
rm -- "$file"                       # 如果 $file 以 - 开头，不会被当成选项
cp -- "$src" "$dst"
```

### 2. 命令注入：永远不要把不可信的数据当作代码

```bash
input='hi; echo INJECTED'
bash -c "echo $input"               # 输出 hi 和 INJECTED：分号后面的内容被当成了命令
bash -c 'echo "$1"' _ "$input"      # 安全：数据通过参数传入，不会被解释为代码
```

最危险的几种写法：`eval "...$input..."`、`bash -c "...$input..."`、`sh -c "...$input..."`、拼接了用户输入的 `ssh host "cmd $input"`。第 11 章会专门讲 `eval`。

### 3. 用数组构造命令，而不是拼字符串

```bash
cmd=(tar -czf "$out")
if [ "$verbose" -eq 1 ]; then cmd+=(-v); fi     # 选项要在 -- 之前追加
cmd+=(-C "$dir" -- "$name")
"${cmd[@]}"                         # 每个元素是一个独立的参数，空格、引号都不会出问题
```

注意追加的顺序：`--` 之后的内容都会被当作文件名，所以条件性的选项必须在 `--` **之前**加入数组。

### 4. 给危险操作加护栏

```bash
rm -rf -- "${dir:?}/"               # dir 为空或未设置时直接报错退出，不会变成 rm -rf /
```

对于要删除的路径，再加一层检查更稳妥：

```bash
case "$dir" in
    ""|"/"|"$HOME") die "拒绝删除: $dir" ;;
esac
```

### 5. 临时文件、权限

- 临时文件用 `mktemp`（10.5）
- 会写出敏感内容的脚本，先 `umask 077`（第 9 章）

### 6. 不要把密码放在命令行参数里

命令行参数能被同一台机器上的其他用户用 `ps` 看到。更好的做法是：从权限为 `600` 的文件读取、使用工具自带的凭据机制（如 ssh 密钥），或在必要时从环境变量或标准输入传入。

### 7. 不要解析 `ls` 的输出

文件名里可以有空格、换行，`for f in $(ls)` 一定会出问题。用 glob 或 `find -print0`：

```bash
for f in ./*.txt; do [ -e "$f" ] || continue; ...; done
find . -name '*.txt' -print0 | xargs -0 ...
```

### 8. 以 root 或 sudo 运行的脚本要格外小心

- 先校验输入，再使用
- 不要信任调用者的 `PATH`，需要时在脚本开头设置 `PATH`
- 不要写 `curl ... | sudo bash`，先下载、看过再运行

## 10.10 编码规范速查

好的规范能让脚本更容易读、更少出错。下面是一份常见的清单（也可参考 Google 发布的 Shell Style Guide，内容可能更新，以原文为准）：

| 方面 | 建议 |
|------|------|
| 文件头 | 第一行 shebang，随后用注释写明用途、用法、依赖 |
| 严格模式 | `set -euo pipefail`（并理解它的局限，10.2） |
| 命名 | 变量和函数用 `lower_snake_case`；常量、环境变量用 `UPPER_SNAKE_CASE`，常量加 `readonly` |
| 作用域 | 函数里的变量一律 `local`；逻辑放进函数，最后 `main "$@"` |
| 引号 | 变量展开默认加双引号（`"$var"`、`"$@"`、`"$(cmd)"`） |
| 测试 | bash 里用 `[[ ]]` 做字符串/文件判断，`(( ))` 做数值判断；要可移植时用 `[ ]` |
| 命令替换 | 用 `$(...)`，不用反引号 |
| 输出 | 数据用 `printf`，错误信息到 stderr |
| 缩进 | 统一用空格（2 或 4 个），不要混用 |
| `cd` | 总是检查：`cd "$dir" \|\| exit` |
| 可读性 | 复杂命令用长选项（`--recursive` 比 `-r` 更易懂），长命令用 `\` 续行 |
| 检查 | 提交前跑 `bash -n` 和 `shellcheck` |
| 规模 | 脚本超过几百行、需要复杂数据结构时，考虑换用更适合的语言 |

## 10.11 综合模板：健壮脚本

`template.sh`：合并读取若干文件，去重排序后输出到 stdout 或指定文件。它把本章的技巧都用上了：严格模式、日志、`die`、`ERR`/`EXIT` 陷阱、`mktemp`、`getopts`、依赖检查。

```bash
#!/usr/bin/env bash
#
# template.sh - 合并若干文本文件，去重并排序
# 用法: template.sh [-v] [-o 输出文件] 输入文件...
# 依赖: bash, sort, mktemp

set -Eeuo pipefail

readonly PROG="${0##*/}"
VERBOSE=0
WORKDIR=""

usage() {
    cat >&2 <<EOF
用法: $PROG [-v] [-o 输出文件] 输入文件...
  -o FILE   把结果写入 FILE（默认输出到标准输出）
  -v        显示调试信息
  -h        显示帮助
EOF
}

log()   { printf '%s [%s] %s\n' "$(date '+%F %T')" "$1" "${*:2}" >&2; }
info()  { log INFO "$@"; }
debug() { if [ "$VERBOSE" -eq 1 ]; then log DEBUG "$@"; fi; }
die()   { log ERROR "$@"; exit 1; }

cleanup() {
    if [ -n "$WORKDIR" ]; then
        rm -rf -- "$WORKDIR"
    fi
}
on_err() { log ERROR "第 $1 行出错: $2 (状态 $3)"; }

trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
trap 'on_err "$LINENO" "$BASH_COMMAND" "$?"' ERR

main() {
    local output="" opt f
    while getopts ":vo:h" opt; do
        case "$opt" in
            v)  VERBOSE=1 ;;
            o)  output="$OPTARG" ;;
            h)  usage; exit 0 ;;
            :)  echo "选项 -$OPTARG 需要参数" >&2; usage; exit 2 ;;
            \?) echo "未知选项: -$OPTARG" >&2; usage; exit 2 ;;
        esac
    done
    shift $((OPTIND - 1))

    if [ $# -lt 1 ]; then
        usage
        exit 2
    fi

    command -v sort >/dev/null 2>&1 || die "缺少依赖: sort"

    WORKDIR="$(mktemp -d "${TMPDIR:-/tmp}/${PROG}.XXXXXX")"
    debug "工作目录: $WORKDIR"

    for f in "$@"; do
        [ -r "$f" ] || die "无法读取: $f"
        debug "读取 $f"
        cat -- "$f" >> "$WORKDIR/all.txt"
    done

    sort -u -- "$WORKDIR/all.txt" > "$WORKDIR/out.txt"

    if [ -n "$output" ]; then
        mv -- "$WORKDIR/out.txt" "$output"
        info "已写入 $output"
    else
        cat -- "$WORKDIR/out.txt"
    fi
}

main "$@"
```

> 注意：模板里报告"用法错误"用的是 `exit 2`，而不是第 7 章模板里的 `return 2`。
> 原因是：开启了 `ERR` 陷阱后，`return` 一个非 0 的状态会被当成"一次出错"，陷阱会多打印一行
> `第 N 行出错: return 2`，对于用户自己输错参数这种预期内的情况，这行信息是多余的。

试一试：

```bash
printf 'b\na\nb\n' > f1.txt
printf 'c\na\n'     > f2.txt
./template.sh -v f1.txt f2.txt              # 输出 a b c，调试信息在 stderr
./template.sh -o merged.txt f1.txt f2.txt   # 结果写入 merged.txt
./template.sh nofile.txt; echo $?           # 报错，状态 1
./template.sh; echo $?                      # 用法提示，状态 2
```

## 本章小结

- 默认出错继续执行是危险的；`set -e`、`set -u`、`set -o pipefail` 是安全网，但各有例外和坑，**不能代替显式的错误检查**。
- 错误处理：`cmd || die "..."`、`trap ERR` 报告位置、`trap EXIT` 清理、重试函数；错误信息写 stderr。
- 输出数据用 `printf`；临时文件用 `mktemp` 并用 `trap` 清理。
- ShellCheck 做静态检查，`bash -n` 查语法，`set -x`（配合 `PS4`）跟踪执行，注意别泄露敏感信息。
- 可移植性：先确定目标是 bash 还是 POSIX sh；GNU 与 BSD 工具有差异，写明依赖。
- 安全：加引号、用 `--`、不拼接代码、用数组构造命令、`${dir:?}` 护栏、不在命令行放密码。

1. 写一个脚本：开头 `set -e`，演示下面三种情况哪些会让脚本退出，运行验证你的判断：① `false`；② `if false; then :; fi`；③ `false || true`。
2. 写出下面脚本的输出，并解释原因（先判断再运行）：

   set -e
   f() { false; echo "A"; }
   f
   echo "B"
   if f; then echo "C"; fi
   ```

   if [[ $name == A* && -f $file ]]; then echo yes; fi
   echo -e "a\tb"
   ```
9. 找一个你之前写过的脚本，用 `shellcheck` 检查（如果已安装），逐条处理警告；没有安装时，用 `bash -n` 检查并人工对照 10.10 的清单。
10. 解释：为什么 `local out=$(false)` 即使开着 `set -e` 也不会退出？

### 参考答案要点

```bash
# 1
# ① 退出  ② 不退出  ③ 不退出

# 2
# 直接调用 f 时，f 里的 false 触发 set -e，脚本在那里退出：什么都不输出，退出状态 1。
# 如果去掉前面直接调用 f 的那两行，只保留 if f; then echo "C"; fi，
# 则 f 处于条件上下文，函数内的 set -e 失效：先打印 A，f 成功，再打印 C。

# 3
set -u
echo "hello, ${1:-world}"

# 4
false | true; echo $?                 # 0
set -o pipefail; false | true; echo $?  # 1
yes | head -n 1; echo $?              # pipefail 下通常是 141

# 5
count_file=$(mktemp)
echo 0 > "$count_file"
flaky() {
    local n; n=$(cat "$count_file"); n=$((n + 1)); echo "$n" > "$count_file"
    [ "$n" -ge 3 ]
}
retry 5 0 flaky && echo "最终成功"

# 6
tmpdir=$(mktemp -d)
trap 'rm -rf -- "$tmpdir"' EXIT
trap 'exit 143' TERM
trap 'exit 130' INT

# 8
case $name in A*) [ -f "$file" ] && echo yes ;; esac
printf 'a\tb\n'
```

- 第 7 题：`ps` 会显示每个进程完整的命令行，所有用户都能看到；替代做法：从权限 `600` 的文件读取密码，或使用密钥认证。
- 第 10 题：`local out=$(false)` 的退出状态是 `local` 这个内建命令本身的状态（成功，0），不是 `false` 的；应拆成 `local out` 和 `out=$(false)` 两行。

## 常见问题速查

| 现象 | 原因 |
|------|------|
| 脚本莫名其妙退出了 | `set -e` 配合 `((i++))`（值为 0）、`grep` 没匹配、`cmd \| grep` 等返回非 0 的命令 |
| `unbound variable` | 用了没设置的变量；加默认值 `${var:-}`，或检查变量名拼写 |
| 空数组触发 `unbound variable` | bash 4.3 及更早（含 macOS 的 3.2）的限制；升级或先判断数组长度 |
| `pipefail` 下管道莫名失败（状态 141） | SIGPIPE：右边命令提前退出，左边继续写 |
| `set -e` 在函数里不起作用 | 函数在 `if`、`\|\|`、`&&` 等条件上下文里被调用 |
| `sed -i` 在 macOS 报错 | BSD sed 要求 `-i` 后带后缀参数，用 `-i.bak` |
| `/bin/sh` 下报 `[[: not found` 或 `Syntax error` | 在 sh（如 dash）里用了 bash 特性 |
| `mktemp: too few X's in template` | 模板末尾的 `X` 不够（至少 6 个，以本机为准） |
| `set -x` 输出里出现了密码 | `set -x` 会打印展开后的命令，敏感操作前先 `set +x` |
