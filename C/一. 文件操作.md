## 1. 打开和创建文件

![[Pasted image 20260927090925.png]]
**后9位：三组权限，每组3位（rwx）**

- `r` (read, 值4)：可读
- `w` (write, 值2)：可写
- `x` (execute, 值1)：可执行（对目录来说，是"可以进入/列出内容"的权限）
- `-` 表示没有该权限

| 八进制 | 权限  | 典型用途  |
| --- | --- | ----- |
| 4   | r-- | 只读    |
| 5   | r-x | 只读+执行 |
| 6   | rw- | 读写    |
| 7   | rwx | 读写执行  |
| 0   | --- | 无任何权限 |

### 1.1 open()
`open()` 是 POSIX 系统调用（在 Linux/Unix 系统上使用），用于打开或创建文件，返回一个文件描述符（file descriptor）。使用时需要包含头文件
```c
#include <fcntl.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <unistd.h>
```
### 1.2 函数原型
```c
int open(const char *pathname, int flags);
int open(const char *pathname, int flags, mode_t mode);
```

- **pathname**：要打开的文件路径
- **flags**：打开方式的标志位（必选一个，可以用 `|` 组合多个）
- **mode**：仅当 flags 中包含 `O_CREAT` 时才需要，指定新建文件的权限
- **返回值**：成功返回文件描述符（非负整数）；失败返回 `-1`，并设置 `errno`
### 1.3 常用 flags

必选其一（互斥）：
- `O_RDONLY`：只读
- `O_WRONLY`：只写
- `O_RDWR`：读写

可选附加（用 `|` 组合）：
- `O_CREAT`：文件不存在则创建
- `O_EXCL`：与 `O_CREAT` 一起用，若文件已存在则报错（常用于避免覆盖）
- `O_TRUNC`：如果文件存在，打开时清空内容
- `O_APPEND`：写入时追加到文件末尾
- `O_NONBLOCK`：非阻塞模式打开

### 1.4 示例
#### 1.4.1 打开一个已存在的文件（只读）
```rust
int fd = open("test.txt", O_RDONLY);
if (fd == -1) {
    perror("open failed");
    return 1;
}
```

#### 1.4.2 创建新文件（不存在则创建，权限 0644）
```rust
int fd = open("test.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fd == -1) {
    perror("open failed");
    return 1;
}
```
这里的 `0644` 是八进制权限（rw-r--r--），会与进程的 `umask` 做运算后生效。

### 2.1 open()

- 没有 `FILE` 结构体——`fd` 就是一个裸的 `int`,不再被包在某个结构体里,你 stack 上看到的就是一个数字(比如3),没有"缓冲区指针"、"缓冲区位置"、"状态标志"这些字段
- 没有用户态的 Buffer，你要读多少数据,得自己在用户态声明一块内存(比如 `char buf[1024]`),`read()` 会直接把数据拷贝到你指定的这块内存里,再没有中间商

## 3. 读取文件
### 2.1 read()
用 `read()`(不带缓冲)时,流程简单粗暴很多:
1. 你调 `read(fd, buf, 10)`,想读10字节
2. 每一次调用,都直接陷入内核态——没有中间缓冲区帮你挡一道,内核检查页缓存里有没有对应数据
3. 页缓存命中 → 直接从页缓存拷给你的 `buf`;没命中 → 先从磁盘读进页缓存,再拷给你的 `buf`
4. 返回用户态,这次 `read()` 结束

**read和fread的关键区别**:如果你要反复读小块数据(比如一次读1字节,连续读1000次),`fread()` 因为有用户态buffer挡着,可能全程只触发1次系统调用(第一次把4KB读进buffer,后面999次都直接从buffer拿);而 `read()` 则是读一次就陷入一次内核,1000次读取=1000次系统调用,开销大很多——这也是为什么标准库要在 `read()` 外面包一层buffer的根本原因
### 2.2 如果把这个buf数组调大，还会有区别吗？
大 buf 确实能减少系统调用次数，如果你一次 `read(fd, buf, 4096)`,内核会尽量一次性把4096字节都拷给你(受限于内核实际能提供多少),这样你确实不需要读4096次1字节,好处是实打实的。

但和 `fread` 的 Buffer 有本质区别——"一次性" vs "可持续的状态"

**你的 `buf`——是"一次性收货箱"**
第1次 read(fd, buf, 4096) → 内核给了4096字节 → 你处理完这一批
第2次 read(fd, buf, 4096) → 又要重新陷入内核问一次 → 内核再给数据

每次调用 `read()`,都会陷入内核,不管你buf多大——因为你的 `buf` 只是一块裸内存,它不记得"上次读到哪了、这次buf里还剩多少没处理完的数据"。用完一批,下次还得重新找内核要。

**`FILE*` 的 Buffer——是"带状态的仓库",有自己的"库存记录"**
`FILE` 结构体有几个字段:"缓冲区指针"、"缓冲区位置"、"状态标志"——这几个字段的作用就是记录这个buffer当前读到哪了、还剩多少没用完

fread(小块) → 查FILE结构体记录的"缓冲区位置" → buffer里还有剩 → 直接给你,不陷入内核
fread(小块) → 查"缓冲区位置" → 又要一块 → 还有剩 → 继续给,不陷入内核
...(反复很多次都不用陷入内核)...
fread(小块) → 发现buffer里的数据被取完了 → 这才陷入内核,重新灌满buffer

**所以核心区别不是"大不大",而是"有没有配套的记账机制"**
如果你自己写代码,也完全可以手动模拟出 `fread` 的效果:自己声明一个大 `buf`,自己再声明几个变量记录"当前读到buf的第几个字节了"、"buf里一共有效多少字节",每次要读小数据时,先查这几个变量,不够了才调 `read()` 重新灌满——这其实就是在用户态,自己重新实现了一遍 `FILE*` 干的事

**一句话总结**:大 `buf` 只解决了"一次能拿到更多数据",但如果没有额外的变量去记录"这批数据用到哪了",每次 `read()` 调用还是会重新陷入内核；`fread` 真正的优势在于 `FILE` 结构体里那几个"记账"字段,让同一批数据可以被多次小额消费而不用反复问内核要——这才是"缓冲区"这个词真正值钱的地方。
### 2.3 read的一个坑点
```c
char buf[4096];
// 第一次:读进4096字节,假设你只处理了前100字节就不管了
read(fd, buf, 4096);   
// 第二次:又读4096字节,直接从"文件当前的读取位置"继续往下读
// buf 里原来剩下的3996字节数据,直接被覆盖,彻底丢了
read(fd, buf, 4096);   
```

**第二次 `read()` 读到的,是文件里"接着上次读完的位置"往后的新数据,不是"重新发一遍上次没用完的"。因为:**
- 内核那边,每个打开的文件都有一个文件读写位置指针(offset),记录"当前读到哪了",每次 `read()` 成功后,这个指针会自动往前移动(移动的量=这次实际读到的字节数)
- 内核根本不知道、也不关心你 `buf` 里那3996字节你到底用完了没有——它只负责"你要多少,我从当前位置给你多少,然后指针前移"
- 所以你如果没在调用下一次 `read()` 之前,先把 `buf` 里剩下的3996字节处理/保存好,这些数据就真的没了,而且更糟的是——你还跳过了这部分数据对应的文件内容,因为文件指针已经往前挪了

**这正是 `FILE*` 缓冲区"记账"机制存在的意义**
回到上一轮说的:`FILE` 结构体里那个"缓冲区位置"字段,干的就是防止你这个问题的事——它记录着"buffer里的数据,用到第几个字节了",下次 `fread()` 小块数据时,先看这个位置,buffer里还有剩就直接给,绝不会去调新的 `read()` 覆盖掉还没用完的数据,只有确认buffer完全用尽了,才会再去问内核要新的一批。

**所以你想用裸 `read()` 自己实现"不丢数据的大buffer",必须自己补上这个逻辑**
```c
char buf[4096];
int buf_len = 0;      // buf里当前有效数据的总长度
int buf_pos = 0;       // 已经消费到第几个字节了(对应FILE结构体的"缓冲区位置")

// 每次要读小数据时:
if (buf_pos >= buf_len) {          // 判断buffer是否已耗尽
    buf_len = read(fd, buf, 4096); // 耗尽了才重新灌
    buf_pos = 0;
}
// 从 buf[buf_pos] 开始取你要的数据,再让 buf_pos 往前移
```
### 2.4 如果用read模拟fread?
可以创建两个数组，一个大数组，负责从内核读取数据，一个小数组，从大数组中读取数据来进行使用，还要有len和pos记录大数组的总长度和当前已经消费到第几个字节。**详情看2.3**
### 2.5 fread()
当你第一次读取数据的时候，缓存中还没有数据，此时触发read()，程序陷入内核态，内核会根据FILE结构体中存储的文件描述符,去操作系统维护的"打开文件表"，里查到这个文件具体对应磁盘上哪个位置，系统会一次性把数据加载到内核态的页缓存，然后，从页缓存读取4KB字节，存入到用户态的缓存区，然后从用户态的缓存区读取数据，之后读取数据时，首先会到自己的缓冲区查看是否有还没有读完的数据，如果有，则从缓冲区读取，如果没有（缓冲区未命中），此时会调用read（），程序会再次陷入内核态，重复复制操作。
## 4. 写入文件
### 4. 1 write()
```c
write(fd, buf, 100); // 这100字节,直接、立刻陷入内核
```

1. 你把数据准备好放进自己的 `buf`(这个buf只是你自己的临时存放处,不是什么"官方缓冲区")
2. 调用 `write(fd, buf, 100)` → 立刻陷入内核态没有"攒一攒再发"这回事
3. 内核把这100字节,从你的 `buf` 拷贝到内核态的页缓存里(对应我们之前聊的:到这一步,内核就认为这次写操作完成了,`write()` 返回,但数据不一定已经落盘,可能还在页缓存里等着后台刷)
4. 函数返回,继续往下执行

如果你要写100次、每次10字节的小数据,`fwrite()` 可能全程只触发1次系统调用(凑够一个buffer量才真正write);而裸 `write()` 是写一次就陷入内核一次,100次调用=100次系统调用,开销明显更大——逻辑和 `read()` 那边完全对称,只是方向反过来(一个是"攒够了再交给内核",一个是"攒够了再向内核要")

write(fd, data1, ...);  // 陷入内核1次
write(fd, data2, ...);  // 陷入内核1次
write(fd, data3, ...);  // 陷入内核1次

### 4.2 write的一个坑点
`read()` 那边你发现的问题是"buf里没处理完的数据会被下一次read覆盖"。`write()` 这边不存在"覆盖"这个问题(因为是你主动把数据发出去,不是被动接收),但有个对应的坑是:

每次 `write()` 调用返回时,不保证100字节全都写进去了——`write()` 的返回值是"实际写入的字节数",可能小于你要求的数量(比如磁盘满了、或者是网络socket发送缓冲区暂时满了)。这时候你需要检查返回值,如果没写完,得自己写循环,把剩下的部分再调一次 `write()` 补上——这也是标准库 `fwrite()` 帮你屏蔽掉的一个麻烦事,它内部已经处理好了"写不完就重试"这个逻辑,你用 `fwrite()` 从来不用操心这个
### 4.3 如何用write模拟fwrite?
同样也是创建两个数组，一个大数组，负责记录写入的内容和位置，一个小数组负责往大数组里写入数据，同样要有len和pos两个变量
### 4.4 fwrite()
数据会先存入到buffer中，等到凑够了一个buffer的量，一次性，写入到内核的页缓存
## 5. fflush()

`fflush()` 只用在写这边,读的时候基本用不上——这不是对称的
只有fwrite是会用到，因为fwrite，会先写入到自己的缓存

### 5.1 `fflush()` 是干什么的
强制把 `FILE*` 用户态缓冲区里还没交给内核的数据,立刻触发 `write()` 系统调用,送进内核(不等缓冲区自然写满、也不等程序退出)

### 5.2 什么时候需要手动 `fflush()`——写的场景
正常情况下,缓冲区满了/程序正常退出/`fclose()` 时,数据自然会被刷出去,你不用管。但有几种情况,你必须手动催一下
#### 5.2.1 你要求立刻看到输出,但缓冲策略不允许
```c
// 如果stdout连着终端且是行缓冲,没有\n,这句可能卡在buffer里不显示
printf("正在处理...");   
// 手动催一下,强制显示出来
fflush(stdout);          
```
如果 `stdout` 被重定向到文件(变成全缓冲),即使有换行符也不会自动刷新,这时候更需要手动 `fflush()`
#### 5.2.2 程序可能异常崩溃,担心数据丢在buffer里没来得及自然刷新
比如写日志,你希望每条日志写完立刻落到文件里,防止程序万一崩溃时,缓冲区里那部分还没写的日志就永久丢失了
```c
fprintf(log_fp, "关键错误发生\n");
fflush(log_fp);   // 立刻推给内核,不等buffer满
```
注意:`fflush()` 只保证数据到了内核页缓存,不保证真的落盘了——这是我们前面聊过的,如果要保证真落盘,还得再调 `fsync()`,这是更深一层的保证,`fflush` 管不到磁盘这一层
#### 5.2.3 多个流交替写同一个终端,防止顺序错乱
比如你同时往 `stdout` 和 `stderr` 输出,因为两者缓冲策略不同(`stdout`行缓冲/全缓冲,`stderr`无缓冲),显示顺序可能和你代码里写的顺序对不上,这时候适当 `fflush(stdout)` 能让顺序更符合预期。
### 5.3 读的场景为什么基本不需要 `fflush()`
`fflush()` 的语义是"把还没发出去的数据强制发出去"——这个概念只对写缓冲区有意义(缓冲区里躺着的是"你已经生产、但还没交给内核"的数据)。

读缓冲区里躺着的东西,是"内核已经给你、但你还没消费完"的数据——这些数据不需要"催",它们已经在你手里了,只是你还没读到那部分而已,不存在"卡住没发出去"这个问题。你对着一个只读打开的 `FILE*` 调 `fflush()`,C标准里这是未定义行为(不同实现可能什么都不做,或者报错),不是一个有意义的操作
### 5.4 一句话总结

`fflush()` 只用在写场景,作用是把用户态buffer里还没交给内核的数据强制推出去,常见于"要立刻看到输出"或"怕崩溃丢数据"这两种情况;读场景不需要它,因为读缓冲区里的数据是"已经拿到手、等你自己去用"的,没有"催促发送"这回事
## 6. 流（C标准对open, read和write的封装）
### 6.1 三个预定义的流,类型是 `FILE*` 
```c
FILE *stdin;    // 标准输入
FILE *stdout;   // 标准输出
FILE *stderr;   // 标准错误
```
C标准规定:程序启动时,这三个流已经打开,不需要你调用 `fopen()`,可以直接使用
### 6.2 三种缓冲模式
C标准规定了缓冲区必须支持这三种模式,通过 `setvbuf()` 可以设置:
- `_IOFBF`——全缓冲(Fully Buffered)
- `_IOLBF`——行缓冲(Line Buffered)
- `_IONBF`——无缓冲(Not Buffered)
标准里提到,`stderr` 应该是**不完全缓冲**的(标准原文措辞大概是"不应比其他流缓冲更多",实际各家实现基本都做成无缓冲)
### 6.3 `stdin` — 从键盘/标准输入读取
```c
#include <unistd.h>

int main() {
    char buf[100];
    ssize_t n = read(0, buf, sizeof(buf));   // 从fd=0(stdin)读取键盘输入
    write(1, buf, n);                         // 读到多少,写回屏幕验证一下
    return 0;
}
```
### 6.4 `stdout` — 往屏幕(终端)输出
```c
#include <unistd.h>
#include <string.h>

int main() {
    char *msg = "这是正常输出\n";
    write(1, msg, strlen(msg));   // 直接写到fd=1,不经过printf/FILE缓冲
    return 0;
}
```
### 6.5 `stderr` — 专门输出错误信息
```c
#include <unistd.h>
#include <string.h>

int main() {
    char *msg = "这是错误信息\n";
    write(2, msg, strlen(msg));   // 直接写到fd=2
    return 0;
}
```
