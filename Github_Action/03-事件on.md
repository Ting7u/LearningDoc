# 第 3 节：事件 `on`（什么时候运行）

> 本节目标：搞懂 `on` 这一块怎么写，能让 workflow 在你想要的时机触发。
> 对应全景图里最前面的那个方块：**Event（事件）**。
---
## 1. `on` 在整体中的位置
```
 ┌──────────────┐
 │  on（事件）   │  ← 本节：什么时候运行？
 └──────┬───────┘
        ▼
 ┌──────────────┐
 │  jobs        │  ← 下一节：运行什么？
 └──────────────┘
```

`on` 属于 **Workflow 级**关键字，写在文件顶层。

---
## 2. 事件的三大类
GitHub 的事件有几十种，但可以归成三类，记住这三类就够了：

```
                        on（触发方式）
          ┌──────────────────┼──────────────────┐
          ▼                  ▼                  ▼
    ① 仓库活动事件       ② 定时触发          ③ 手动触发
    （代码/协作行为）     （闹钟）            （点按钮）
          │                  │                  │
    push                 schedule         workflow_dispatch
    pull_request         （cron 表达式）
    release
    issues ...
```

| 类别     | 典型场景                    |
| ------ | ----------------------- |
| ① 仓库活动 | push 代码后自动测试；提 PR 时自动检查 |
| ② 定时   | 每天凌晨自动备份、每周自动生成报告       |
| ③ 手动   | 点一下按钮，执行部署或发布           |

---
## 3. `on` 的三种写法
同样是 `on`，写法由简到繁有三种：
### 写法一：单个事件
```yaml
on: push
```

### 写法二：多个事件（列表）
```yaml
on: [push, pull_request]
```

意思是：push 或 pull_request，任意一个发生都会触发。
### 写法三：带配置（最常用）
```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
```

当你需要给事件加**过滤条件**时，就要用这种写法：事件名后面加冒号，再缩进写配置。

```
选择哪种写法？
 ├── 不需要过滤        →  写法一 / 写法二
 └── 需要加条件、过滤   →  写法三
```

> 注意写法三里 `workflow_dispatch:` 后面什么都没有也是合法的，表示"不带配置"。

---
## 4. 重点事件一：`push`
**触发时机**：有人把代码推送到仓库。
### 基础用法
```yaml
on: push
```

任何分支的任何 push 都触发。
### 加过滤：只在指定分支触发
```yaml
on:
  push:
    branches:
      - main
      - dev
```

只有推送到 `main` 或 `dev` 才触发，推到其他分支不触发。
### 加过滤：按文件路径
```yaml
on:
  push:
    paths:
      - 'src/**'
```

只有 `src/` 目录下的文件有改动才触发。比如只改了 `README.md`，就不会运行。
### 常用过滤选项

| 选项                | 作用             | 例子           |
| ----------------- | -------------- | ------------ |
| `branches`        | 只在这些分支触发       | `[main]`     |
| `branches-ignore` | 这些分支不触发        | `[test/**]`  |
| `paths`           | 只有这些路径变了才触发    | `['src/**']` |
| `paths-ignore`    | 这些路径变了不触发      | `['**.md']`  |
| `tags`            | 只在推送这些 tag 时触发 | `['v*']`     |

> 通配符：`*` 匹配单层（不含 `/`），`**` 匹配多层。例如 `feature/*` 匹配 `feature/login`，不匹配 `feature/a/b`；`feature/**` 两者都匹配。

---
## 5. 重点事件二：`pull_request`
**触发时机**：PR 被创建、更新等。典型用途：**合并之前自动跑测试**，把关代码质量。

```yaml
on:
  pull_request:
    branches: [main]
```

```
dev 分支  ──提 PR──►  main 分支
                      ↑
        这里的 branches 指的是 PR 的"目标分支"
        （要合并进哪个分支），不是来源分支
```

默认情况下，以下三种动作会触发：

| 动作          | 含义          |
| ----------- | ----------- |
| opened      | 新建 PR       |
| synchronize | PR 里又推送了新提交 |
| reopened    | 重新打开 PR     |

所以你在 PR 里每多推一次代码，测试就会自动重跑一次。
### push 和 pull_request 的区别

```
push          →  代码已经推上去了，事后检查
pull_request  →  代码还没合并，事前检查（更适合做把关）
```

实际项目里常常**两个都写**：

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

---
## 6. 重点事件三：`schedule`（定时）
**触发时机**：到了设定的时间点，像闹钟一样。使用 **cron 表达式**。

```yaml
on:
  schedule:
    - cron: '0 1 * * *'
```

### cron 的 5 个字段

```
┌───────────── 分钟 (0-59)
│ ┌─────────── 小时 (0-23)
│ │ ┌───────── 日   (1-31)
│ │ │ ┌─────── 月   (1-12)
│ │ │ │ ┌───── 星期 (0-6，0 是周日)
│ │ │ │ │
* * * * *
```

`*` 表示"每一个"。

### 常见例子

| 表达式           | 含义            |
| ------------- | ------------- |
| `0 1 * * *`   | 每天 UTC 01:00  |
| `30 8 * * 1`  | 每周一 UTC 08:30 |
| `0 */6 * * *` | 每 6 小时一次      |
| `0 0 1 * *`   | 每月 1 号 00:00  |

### ⚠️ 三个必须注意的点
1. **时间是 UTC，不是本地时间**
   你在台湾（UTC+8），要在台湾时间早上 9:00 运行，就得减 8 小时：

   ```
   台湾 09:00  =  UTC 01:00   →   cron: '0 1 * * *'
   ```

2. **不精确**：高峰期可能延迟几分钟甚至更久，不适合对时间要求严格的任务
3. **只在默认分支上生效**：定时任务读取的是默认分支（通常是 main）里的 workflow 文件。另外，公开仓库如果 60 天没有任何活动，定时任务会被自动停用

## 7. 重点事件四：`workflow_dispatch`（手动）
**触发时机**：你在 GitHub 网页上点按钮。

```yaml
on:
  workflow_dispatch:
```

效果：Actions 页面左侧选中该 workflow，右边会出现 **Run workflow** 按钮。

```
Actions 页面
┌────────────────────────────────────────┐
│ 此 workflow 支持手动触发                 │
│                      [ Run workflow ▾ ]│  ← 点它
└────────────────────────────────────────┘
```

### 可以带输入参数

```yaml
on:
  workflow_dispatch:
    inputs:
      name:
        description: '你的名字'
        required: true
        default: 'World'

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello, ${{ inputs.name }}!"
```

点按钮时会弹出输入框让你填 `name`，然后在步骤里用 `${{ inputs.name }}` 取到。

> `${{ }}` 是表达式语法，用来读取数据，后面第 6 节会专门讲，这里先混个眼熟。

> 注意：手动触发的按钮要在 **workflow 文件存在于默认分支** 之后才会出现。

## 8. 其他常见事件（了解即可）

| 事件              | 触发时机             | 典型用途      |
| --------------- | ---------------- | --------- |
| `release`       | 发布 Release       | 自动打包、发布   |
| `issues`        | Issue 被创建/修改     | 自动打标签、回复  |
| `issue_comment` | 有人评论             | 机器人响应命令   |
| `workflow_call` | 被其他 workflow 调用  | 可复用流程（进阶） |
| `workflow_run`  | 另一个 workflow 结束后 | 串联多个流程    |

现在不用深究，用到时再查官方文档 *Events that trigger workflows*。

## 9. 综合示例
一个常见的组合：

```yaml
name: CI

on:
  push:
    branches: [main]          # 推到 main 时跑
    paths-ignore:
      - '**.md'               # 但只改文档时不跑
  pull_request:
    branches: [main]          # 向 main 提 PR 时跑
  schedule:
    - cron: '0 1 * * *'       # 每天台湾早上 9 点跑
  workflow_dispatch:          # 也允许手动点按钮跑

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "触发来源：${{ github.event_name }}"
```

`github.event_name` 会告诉你这次是被哪个事件触发的（`push`、`pull_request`、`schedule`、`workflow_dispatch`），可以用来验证效果。

```
              ┌─ push 到 main（非纯文档）─┐
              ├─ 向 main 提 PR ──────────┤
 触发来源  ───┤                          ├──►  运行 test 任务
              ├─ 每天定时 ───────────────┤
              └─ 手动点按钮 ─────────────┘
```

多个事件之间是 **"或"** 的关系，任意一个满足就触发。

## 10. 动手练习
在你的测试仓库里：

1. 把 hello.yml 的 `on` 改成：
   ```yaml
   on:
     push:
       branches: [main]
     workflow_dispatch:
   ```
2. 在 `steps` 里加一行 `run: echo "事件：${{ github.event_name }}"`
3. push 后观察日志，应该输出 `push`
4. 回到 Actions 页面，点 **Run workflow** 手动触发，再看日志，这次应该输出 `workflow_dispatch`
5. 新建一个分支（如 `test`）并 push，观察：**不会**触发（因为只限定了 main）

## 11. 常见错误

| 问题 | 原因 |
|---|---|
| 推送后 workflow 没运行 | 分支或路径被过滤掉了；或文件不在 `.github/workflows/` |
| 看不到 Run workflow 按钮 | 没写 `workflow_dispatch`，或文件还没合并到默认分支 |
| 定时任务没按时运行 | cron 用的是 UTC；或不在默认分支；或有延迟 |
| `branches` 写了但 PR 没触发 | PR 的 `branches` 看的是**目标分支** |

## 12. 本节小结
1. 事件分三类：**仓库活动、定时、手动**
2. `on` 有三种写法：单个、列表、带配置（需要过滤时用）
3. 最常用的是 **`push`、`pull_request`、`schedule`、`workflow_dispatch`**
4. 过滤手段：`branches`、`paths`、`tags`（及对应的 ignore）
5. cron 用 **UTC 时间**，台湾时间要减 8 小时
6. 多个事件之间是"或"的关系
