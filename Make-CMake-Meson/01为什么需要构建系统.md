## 1.1 C/C++ 编译流程:预处理 → 编译 → 汇编 → 链接

### 1.1.1 准备一个示例项目

后面整个教程都会用到这个小项目,请先建立:

```
demo/
├── include/
│   └── mathutils.h
├── src/
│   ├── main.c
│   └── mathutils.c
```

**include/mathutils.h**

```c
#ifndef MATHUTILS_H
#define MATHUTILS_H

int add(int a, int b);
int mul(int a, int b);

#endif
```

**src/mathutils.c**

```c
#include "mathutils.h"

int add(int a, int b) { return a + b; }
int mul(int a, int b) { return a * b; }
```

**src/main.c**

```c
#include <stdio.h>
#include "mathutils.h"

#define GREETING "Hello, build system!"

int main(void) {
    printf("%s\n", GREETING);
    printf("add(2,3) = %d\n", add(2, 3));
    printf("mul(2,3) = %d\n", mul(2, 3));
    return 0;
}
```

一条命令就能编译:

```bash
gcc -Iinclude src/main.c src/mathutils.c -o app
./app
```

这一条命令背后,其实依次发生了四个阶段。

### 1.1.2 四个阶段总览

```
 main.c ──预处理──▶ main.i ──编译──▶ main.s ──汇编──▶ main.o ──┐
                                                               ├─链接─▶ app
 mathutils.c ─▶ mathutils.i ─▶ mathutils.s ─▶ mathutils.o ─────┘
   (cpp)         (cc1)          (as)                (ld)
```

| 阶段 | 输入 | 输出 | 工具 | 做了什么 |
|---|---|---|---|---|
| 预处理 | `.c` / `.cpp` | `.i` / `.ii` | `cpp`(`gcc -E`) | 展开 `#include`、`#define` 宏、条件编译 `#if`、删除注释 |
| 编译 | `.i` | `.s` | `cc1`(`gcc -S`) | 语法/语义分析、优化,生成汇编代码 |
| 汇编 | `.s` | `.o` | `as`(`gcc -c`) | 汇编代码变成机器码,生成可重定位目标文件 |
| 链接 | 多个 `.o` + 库 | 可执行文件/库 | `ld`(由 `gcc` 驱动) | 合并段、解析符号引用、重定位 |

> 注意:`gcc` 本身只是一个"驱动程序(driver)",它根据参数依次调用 cpp、cc1、as、ld。

### 1.1.3 逐阶段实操

**① 预处理(`-E`)**

```bash
gcc -E -Iinclude src/main.c -o main.i
```

打开 `main.i` 你会看到:`stdio.h` 的几百行内容被原样插入;`GREETING` 被替换成了 `"Hello, build system!"`;文件末尾才是你写的 `main` 函数。

```bash
tail -n 12 main.i
```

可以看出预处理阶段**只做文本替换**,完全不检查语法。

**② 编译(`-S`)**

```bash
gcc -S -Iinclude src/main.c -o main.s
```

得到汇编文本(x86-64 示例,片段):

```asm
main:
    pushq   %rbp
    movq    %rsp, %rbp
    leaq    .LC0(%rip), %rdi
    call    puts@PLT
    movl    $3, %esi
    movl    $2, %edi
    call    add@PLT      ; add 只是一个未解析的符号
    ...
```

注意 `add` 在这里只是一个**符号引用**,编译器此时并不知道它在哪。

**③ 汇编(`-c`)**

```bash
gcc -c -Iinclude src/main.c -o main.o
gcc -c -Iinclude src/mathutils.c -o mathutils.o
```

得到 `.o` 文件(二进制)。用 `nm` 查看符号:

```bash
nm main.o
```

```
                 U add          # U = Undefined,未定义,等待链接时解析
                 U mul
0000000000000000 T main         # T = Text 段中已定义
                 U puts
```

```bash
nm mathutils.o
```

```
0000000000000000 T add
0000000000000014 T mul
```

**④ 链接**

```bash
gcc main.o mathutils.o -o app
```

链接器把 `main.o` 里的 `U add` 与 `mathutils.o` 里的 `T add` 配对,同时从 libc 里找到 `puts`,最终生成可执行文件。

**常见链接错误**

```bash
gcc main.o -o app
# undefined reference to `add'
# undefined reference to `mul'
```

> 记住:**"undefined reference" 是链接错误,不是编译错误**;`fatal error: xxx.h: No such file` 才是预处理阶段的错误。区分错误出在哪个阶段,是排错的第一步。

### 1.1.4 保留中间文件

不想手动一步步执行,可以让编译器保留所有中间产物:

```bash
gcc -save-temps -Iinclude -c src/main.c
ls
# main.i  main.s  main.o
```

### 1.1.5 查看 gcc 实际调用了什么

```bash
gcc -v -Iinclude src/main.c src/mathutils.c -o app
```

输出中会看到 `cc1`、`as`、`collect2`(最终调用 `ld`)的完整命令行。

### 1.1.6 C++ 的额外概念

- **编译单元(Translation Unit)**:一个 `.cpp` 文件经预处理后的结果。每个编译单元**独立编译**,这是增量编译成为可能的基础。
- **名字修饰(Name Mangling)**:C++ 支持重载,编译器会把函数名编码进符号。

```cpp
// foo.cpp
int add(int, int);
double add(double, double);
```

```bash
g++ -c foo.cpp && nm foo.o
# _Z3addii    ← add(int,int)
# _Z3adddd    ← add(double,double)
nm -C foo.o     # -C 解码为可读形式
```

- **`extern "C"`**:C++ 调用 C 库时需要关闭名字修饰:

```c
#ifdef __cplusplus
extern "C" {
#endif
int add(int a, int b);
#ifdef __cplusplus
}
#endif
```

- **模板与内联**:定义放在头文件中,每个使用它的编译单元都会实例化一份,链接器负责去重(ODR 规则)。这也是 C++ 编译慢的原因之一。
- 链接 C++ 程序请用 `g++`(或 `gcc ... -lstdc++`),否则找不到 C++ 标准库。

## 1.2 常用编译器及参数

### 1.2.1 常见编译器

| 编译器 | 平台 | 命令 | 备注 |
|---|---|---|---|
| GCC | Linux/BSD/MinGW | `gcc` / `g++` | GNU 编译器集合 |
| Clang/LLVM | macOS/Linux/Windows | `clang` / `clang++` | 参数兼容 GCC,报错友好 |
| MSVC | Windows | `cl.exe` | 参数风格不同(`/` 开头) |
| clang-cl | Windows | `clang-cl` | Clang 的 MSVC 兼容前端 |
| Intel oneAPI | 多平台 | `icx` / `icpx` | 高性能计算 |
| 交叉编译器 | 嵌入式 | `arm-none-eabi-gcc` 等 | 前缀表示目标平台 |

macOS 上的 `gcc` 实际上通常是 Apple Clang 的别名(`gcc --version` 可验证)。

### 1.2.2 GCC/Clang 常用参数速查

**流程控制**

| 参数 | 含义 | 示例 |
|---|---|---|
| `-E` | 只预处理 | `gcc -E a.c` |
| `-S` | 只编译到汇编 | `gcc -S a.c` |
| `-c` | 只编译汇编,不链接 | `gcc -c a.c` |
| `-o <file>` | 指定输出文件 | `gcc a.c -o app` |
| `-v` | 显示详细过程 | |
| `-save-temps` | 保留中间文件 | |

**路径与库**

| 参数 | 含义 | 示例 |
|---|---|---|
| `-I<dir>` | 头文件搜索路径 | `-Iinclude` |
| `-L<dir>` | 库文件搜索路径 | `-L./lib` |
| `-l<name>` | 链接 `lib<name>.so/.a` | `-lm`(libm)、`-lpthread` |
| `-isystem <dir>` | 系统头文件路径(抑制其中警告) | |
| `-Wl,<opt>` | 把参数传给链接器 | `-Wl,-rpath,/opt/lib` |
| `-static` | 全静态链接 | |
| `-shared` | 生成动态库 | |
| `-fPIC` | 生成位置无关代码 | 动态库必需 |
| `-rdynamic` | 导出可执行文件符号给 dlopen 用 | |

**宏与标准**

| 参数 | 含义 | 示例 |
|---|---|---|
| `-D<name>[=value]` | 定义宏 | `-DDEBUG`、`-DVERSION=\"1.0\"` |
| `-U<name>` | 取消宏 | |
| `-std=<std>` | 语言标准 | `-std=c11`、`-std=c++17` |

**优化与调试**

| 参数 | 含义 |
|---|---|
| `-O0` | 不优化(调试用,默认) |
| `-O1` / `-O2` | 常规优化,`-O2` 是 Release 常用值 |
| `-O3` | 激进优化(向量化、内联) |
| `-Os` | 优化体积 |
| `-Og` | 适合调试的优化 |
| `-g` / `-g3` | 生成调试信息(g3 含宏信息) |
| `-DNDEBUG` | 关闭 `assert`(Release 常配合) |
| `-flto` | 链接时优化 |
| `-march=native` | 针对本机 CPU 指令集优化(不便于分发) |

**警告与检查**

| 参数 | 含义 |
|---|---|
| `-Wall` | 常用警告集合 |
| `-Wextra` | 更多警告 |
| `-Wpedantic` | 严格遵循标准 |
| `-Werror` | 警告当错误 |
| `-Wno-xxx` | 关闭某个警告 |
| `-fsanitize=address,undefined` | 运行时检查(ASan/UBSan) |
| `-fsanitize=thread` | 线程检查(TSan,不能与 ASan 同用) |

**依赖生成**(第 6 章详解)

| 参数 | 含义 |
|---|---|
| `-M` / `-MM` | 输出依赖关系(`-MM` 不含系统头) |
| `-MMD` | 编译同时生成 `.d` 文件(不含系统头) |
| `-MP` | 为头文件添加伪目标,避免头文件删除后 make 报错 |
| `-MF <file>` / `-MT <target>` | 指定依赖文件名 / 目标名 |

### 1.2.3 一个典型的 Debug 与 Release 对比

```bash
# Debug
gcc -std=c11 -Wall -Wextra -O0 -g -DDEBUG -Iinclude src/*.c -o app_debug

# Release
gcc -std=c11 -Wall -Wextra -O2 -DNDEBUG -Iinclude src/*.c -o app_release

ls -l app_debug app_release   # 对比体积
```

### 1.2.4 `CFLAGS` 与 `CPPFLAGS` 的传统分工

| 变量 | 传给谁 | 典型内容 |
|---|---|---|
| `CPPFLAGS` | 预处理器 | `-I`、`-D` |
| `CFLAGS` / `CXXFLAGS` | C / C++ 编译器 | `-O2 -Wall -g` |
| `LDFLAGS` | 链接器 | `-L`、`-Wl,...` |
| `LDLIBS` / `LIBS` | 要链接的库 | `-lm -lpthread` |

> 这是 make 与 Autotools 的约定。后面学 make 时会看到它们被隐含规则使用。

### 1.2.5 MSVC 对照

| GCC/Clang | MSVC |
|---|---|
| `gcc a.c -o a.exe` | `cl a.c /Fe:a.exe` |
| `-c` | `/c` |
| `-I` | `/I` |
| `-D` | `/D` |
| `-O2` | `/O2` |
| `-g` | `/Zi`(配合 `/DEBUG` 链接) |
| `-Wall` | `/W4`(`/Wall` 过于嘈杂) |
| `-std=c++17` | `/std:c++17` |
| `-l` / `-L` | 直接写 `xxx.lib` / `/LIBPATH:` |
| `-shared` | `/LD` |
| `-fPIC` | 不需要(Windows DLL 机制不同) |
| 运行时库选择 | `/MD`(动态 CRT)、`/MT`(静态 CRT)、调试版加 `d` |

## 1.3 目标文件、静态库、动态库

### 1.3.1 三类产物与命名

| 类型 | Linux | macOS | Windows | 特点 |
|---|---|---|---|---|
| 目标文件 | `.o` | `.o` | `.obj` | 单个编译单元的机器码,不可执行 |
| 静态库 | `libfoo.a` | `libfoo.a` | `foo.lib` | `.o` 的归档,链接时拷贝进程序 |
| 动态库(共享库) | `libfoo.so` | `libfoo.dylib` | `foo.dll` + 导入库 `foo.lib` | 运行时加载,多个进程共享 |
| 可执行文件 | 无后缀/`a.out` | 无后缀 | `.exe` | |

Linux 可执行文件格式是 **ELF**,macOS 是 **Mach-O**,Windows 是 **PE**。

### 1.3.2 目标文件内部结构(ELF 简述)

```bash
readelf -S mathutils.o      # 查看段
objdump -d mathutils.o      # 反汇编
size mathutils.o            # 各段大小
```

常见段:

| 段 | 内容 |
|---|---|
| `.text` | 机器指令 |
| `.data` | 已初始化的全局/静态变量 |
| `.bss` | 未初始化的全局/静态变量(不占文件空间) |
| `.rodata` | 只读数据(字符串常量等) |
| `.symtab` / `.strtab` | 符号表 / 字符串表 |
| `.rel.text` / `.rela.text` | 重定位信息 |

`nm` 输出的符号类型:`T`(代码段已定义)、`D`(数据段)、`B`(bss)、`R`(只读)、`U`(未定义);小写表示局部(static)符号。

### 1.3.3 静态库

**创建**:

```bash
gcc -c -Iinclude src/mathutils.c -o mathutils.o
ar rcs libmathutils.a mathutils.o
```

- `r`:插入/替换成员,`c`:创建,`s`:生成符号索引(等价于 `ranlib`)。

**查看**:

```bash
ar t libmathutils.a        # 列出成员
nm libmathutils.a          # 列出符号
```

**使用**:

```bash
gcc -Iinclude src/main.c -L. -lmathutils -o app_static
```

> `-lmathutils` 会让链接器查找 `libmathutils.so` 或 `libmathutils.a`。同一目录同时有两者时**默认优先 `.so`**,可用 `-static` 或 `-l:libmathutils.a` 强制静态。

**静态库的关键行为**:链接器只会从 `.a` 中**提取被引用到的成员 `.o`**。因此:

- **链接顺序很重要**:被依赖的库必须放在依赖者之后。

```bash
# libA 依赖 libB
gcc main.o -lA -lB     # ✔ 正确
gcc main.o -lB -lA     # ✘ 可能 undefined reference
```

- 循环依赖可用 `-Wl,--start-group -lA -lB -Wl,--end-group`。

**优缺点**

| 优点 | 缺点 |
|---|---|
| 运行时无依赖,部署简单 | 可执行文件体积大 |
| 无符号冲突、启动快 | 库更新需重新链接 |
| 便于做静态分发 | 多进程无法共享内存 |

### 1.3.4 动态库

**创建**:

```bash
gcc -fPIC -c -Iinclude src/mathutils.c -o mathutils.o
gcc -shared mathutils.o -o libmathutils.so
# 也可一步:
gcc -fPIC -shared -Iinclude src/mathutils.c -o libmathutils.so
```

- `-fPIC`:Position Independent Code,生成位置无关代码,使库能被加载到任意地址。

**使用**:

```bash
gcc -Iinclude src/main.c -L. -lmathutils -o app_dyn
./app_dyn
# error while loading shared libraries: libmathutils.so: cannot open shared object file
```

运行失败!因为**链接时能找到库(`-L.`),不代表运行时能找到**。解决办法见 1.4 节。

**查看依赖**:

```bash
ldd app_dyn                 # Linux
otool -L app_dyn            # macOS
dumpbin /dependents app.exe # Windows(MSVC 工具)
```

**版本与 soname(Linux)**

真实世界的动态库通常是这样的结构:

```
libfoo.so          → libfoo.so.1          (开发链接名,供 -lfoo 使用)
libfoo.so.1        → libfoo.so.1.2.3      (soname,运行时按它查找)
libfoo.so.1.2.3                           (真实文件)
```

```bash
gcc -shared -fPIC foo.c -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3
ln -s libfoo.so.1.2.3 libfoo.so.1
ln -s libfoo.so.1     libfoo.so
```

- 主版本号变化(1→2)代表 ABI 不兼容;次版本变化代表向后兼容。
- 可执行文件里记录的是 **soname**(`readelf -d app | grep NEEDED`)。

**Windows DLL 的特殊点**

- 需要用 `__declspec(dllexport)` 导出、`__declspec(dllimport)` 导入符号(CMake 的 `GenerateExportHeader` 就是为此,见第 11 章)。
- 链接时使用**导入库** `foo.lib`,运行时加载 `foo.dll`。

**可见性(Linux/macOS)**

```bash
gcc -fvisibility=hidden -fPIC -shared foo.c -o libfoo.so
```

```c
#define API __attribute__((visibility("default")))
API int add(int a, int b);
```

默认所有符号都导出,用 `-fvisibility=hidden` 加显式标注可减小体积、加快加载、避免符号冲突。

**运行时动态加载**:`dlopen/dlsym`(POSIX)、`LoadLibrary/GetProcAddress`(Windows),用于插件系统。对应 CMake 的 `MODULE` 库类型。

### 1.3.5 静态库 vs 动态库 对比

| 维度 | 静态库 | 动态库 |
|---|---|---|
| 链接时机 | 链接期拷贝 | 运行期加载 |
| 可执行文件大小 | 大 | 小 |
| 内存占用 | 各进程各一份 | 可共享代码段 |
| 升级 | 需重新链接 | 替换库文件即可(ABI 兼容时) |
| 部署 | 简单 | 需处理库路径与版本 |
| 典型用途 | 内部模块、嵌入式、单文件分发 | 系统库、插件、大型共享组件 |

## 1.4 头文件搜索路径、库搜索路径、rpath、LD_LIBRARY_PATH

### 1.4.1 头文件搜索路径

**两种 include 写法**

```c
#include "mathutils.h"   // 先找当前源文件所在目录,再找 -I 路径,最后系统路径
#include <stdio.h>       // 跳过当前目录,找 -I 路径,然后系统路径
```

**搜索顺序(GCC)**

1. (仅 `""` 形式)当前源文件所在目录
2. `-iquote` 指定的目录(仅 `""` 形式)
3. `-I` 指定的目录(按命令行顺序)
4. `-isystem` 指定的目录
5. 系统默认目录(如 `/usr/include`、`/usr/local/include`)

**环境变量**:`CPATH`(C/C++ 都有效)、`C_INCLUDE_PATH`、`CPLUS_INCLUDE_PATH`。

**查看编译器的默认搜索路径**:

```bash
echo | gcc -E -Wp,-v -xc -
# 或
gcc -print-search-dirs
```

**实战:`-I` 的作用**

```bash
gcc -c src/main.c -o main.o
# fatal error: mathutils.h: No such file or directory

gcc -Iinclude -c src/main.c -o main.o    # ✔
```

### 1.4.2 库搜索路径(链接期)

链接器按以下顺序找 `-lfoo`:

1. `-L` 指定的目录(按顺序)
2. 环境变量 `LIBRARY_PATH`
3. 系统默认目录(`/lib`、`/usr/lib`、`/usr/local/lib`,多架构系统还有 `/usr/lib/x86_64-linux-gnu` 等)

```bash
gcc -print-search-dirs | grep libraries
ld --verbose | grep SEARCH_DIR
```

### 1.4.3 动态库的运行期搜索(Linux)

可执行文件启动时,动态加载器 `ld.so`(`ld-linux-x86-64.so.2`)按下列顺序查找 `NEEDED` 的库:

1. `DT_RPATH`(若无 `DT_RUNPATH` 才生效;已过时)
2. 环境变量 `LD_LIBRARY_PATH`
3. `DT_RUNPATH`
4. `/etc/ld.so.cache`(由 `ldconfig` 根据 `/etc/ld.so.conf` 及 `/etc/ld.so.conf.d/*.conf` 生成)
5. 默认目录 `/lib`、`/usr/lib`

**解决 1.3.4 中运行失败的四种方法**

**方法 1:`LD_LIBRARY_PATH`(临时、调试用)**

```bash
LD_LIBRARY_PATH=. ./app_dyn
# 或
export LD_LIBRARY_PATH=$PWD:$LD_LIBRARY_PATH
```

缺点:全局影响、容易引发"库冲突"、有安全隐患,**不要用于生产部署**。

**方法 2:rpath / runpath(推荐,写进可执行文件)**

```bash
gcc -Iinclude src/main.c -L. -lmathutils -Wl,-rpath,'$ORIGIN' -o app_dyn
```

- `$ORIGIN` 表示**可执行文件所在目录**,使程序可整体搬迁("可重定位")。
- 常见布局:`-Wl,-rpath,'$ORIGIN/../lib'`(`bin/` 与 `lib/` 并列)。
- 注意在 Makefile 中要写成 `'$$ORIGIN'`。

```bash
readelf -d app_dyn | grep -E 'RPATH|RUNPATH'
chrpath -l app_dyn / patchelf --print-rpath app_dyn   # 工具查看/修改
```

- `-Wl,--enable-new-dtags` 生成 `RUNPATH`(优先级低于 `LD_LIBRARY_PATH`),`-Wl,--disable-new-dtags` 生成 `RPATH`。

**方法 3:安装到系统路径 + `ldconfig`**

```bash
sudo cp libmathutils.so /usr/local/lib/
sudo ldconfig
```

或添加新路径:

```bash
echo "/opt/mylib/lib" | sudo tee /etc/ld.so.conf.d/mylib.conf
sudo ldconfig
ldconfig -p | grep mathutils
```

**方法 4:`-Wl,-rpath-link`**(只影响链接期解析间接依赖,不写入产物)

**排查工具**

```bash
ldd app_dyn                       # 看每个依赖是否 "not found"
LD_DEBUG=libs ./app_dyn           # 打印加载器搜索过程
readelf -d app_dyn | grep NEEDED  # 看直接依赖
```

### 1.4.4 macOS 与 Windows 的对应机制

**macOS**

- 动态库记录一个 **install name**(`install_name`),可执行文件链接时把它拷进去。
- 使用 `@rpath`、`@executable_path`、`@loader_path` 前缀:

```bash
clang -dynamiclib -install_name @rpath/libmathutils.dylib mathutils.c -o libmathutils.dylib
clang main.c -L. -lmathutils -Wl,-rpath,@executable_path -o app
otool -L app
install_name_tool -add_rpath @executable_path/../lib app
```

- 环境变量:`DYLD_LIBRARY_PATH`(受 SIP 限制)。

**Windows**

- 没有 rpath。DLL 搜索顺序(简化):**可执行文件所在目录** → 系统目录 → `PATH` 中的目录。
- 最简单的做法:把 DLL 与 exe **放在同一目录**(CMake 常通过统一输出目录实现)。
- 工具:`dumpbin /dependents`、Dependencies(开源版 Dependency Walker)。

### 1.4.5 小结表

| 环节 | Linux | macOS | Windows |
|---|---|---|---|
| 编译期头文件 | `-I` | `-I` | `/I` |
| 链接期库路径 | `-L` | `-L` | `/LIBPATH:` |
| 运行期库路径 | rpath / `LD_LIBRARY_PATH` / ldconfig | `@rpath` / `DYLD_LIBRARY_PATH` | exe 同目录 / `PATH` |
| 查看依赖 | `ldd` | `otool -L` | `dumpbin /dependents` |

## 1.5 手工编译的痛点

### 1.5.1 阶段一:命令行手写

项目只有 2 个文件时还好:

```bash
gcc -Iinclude src/main.c src/mathutils.c -o app
```

但文件增加到 50 个,**每次改一行都要全部重新编译**——浪费时间。

### 1.5.2 阶段二:写成 Shell 脚本

```bash
#!/bin/bash
set -e
mkdir -p build
for f in src/*.c; do
    gcc -Iinclude -c "$f" -o "build/$(basename "${f%.c}").o"
done
gcc build/*.o -o build/app
```

**问题 1:没有增量编译**。只改了 `main.c`,脚本仍重编所有文件。

### 1.5.3 阶段三:自己做增量判断

```bash
for f in src/*.c; do
    o="build/$(basename "${f%.c}").o"
    if [ ! -f "$o" ] || [ "$f" -nt "$o" ]; then     # 源文件比目标新才编译
        gcc -Iinclude -c "$f" -o "$o"
    fi
done
```

现在碰到**问题 2:头文件依赖**。修改了 `mathutils.h`(比如给 `add` 改了参数类型),但 `main.c` 没动——脚本认为 `main.o` 是最新的而**不重新编译**,结果 `main.o` 仍按旧接口调用,**运行时出现诡异的错误**,而且极难排查。

想要正确,脚本得知道每个 `.c` 依赖哪些 `.h`。靠人手维护依赖列表不可靠,需要 `gcc -MMD` 自动生成(见第 6 章),再自己解析——这已经是在**重新发明构建系统**。

### 1.5.4 痛点汇总

| 痛点 | 具体表现 |
|---|---|
| **增量编译** | 只重编修改过的文件及受影响的文件;需比较时间戳或哈希 |
| **依赖管理** | 头文件依赖、目标之间的依赖(先编库后编程序)、第三方库的查找与版本 |
| **并行构建** | 手写脚本很难正确地并行,且需要保证依赖顺序 |
| **跨平台** | Linux 用 `gcc`/`.so`,Windows 用 `cl`/`.dll`,命令、参数、后缀、路径分隔符都不同 |
| **配置多样性** | Debug/Release、不同编译器、不同选项开关(是否启用某功能)、交叉编译 |
| **目录管理** | 源码外构建、输出目录、安装目录 |
| **可维护性** | 命令越来越长,错误难以定位,新人难以上手 |
| **工具集成** | IDE、静态分析工具、clangd 需要知道每个文件的编译命令(`compile_commands.json`) |
| **安装与打包** | `install`、生成 deb/rpm/zip |
| **测试** | 统一运行测试并汇总结果 |

### 1.5.5 构建系统要解决的问题

**一句话**:给定"源文件 + 它们之间的依赖关系 + 如何生成每个产物的规则",**自动、正确、高效地**生成最终产物。

- **自动**:一条命令完成所有步骤。
- **正确**:改了什么就重编所有受影响的部分,不多也不少。
- **高效**:增量 + 并行 + 缓存。

下一章会讲这些思想如何抽象成**依赖图**,以及 make / CMake / Meson / Ninja 各自处于哪一层。

## 1.6 本章小结

1. 编译流程:**预处理(-E)→ 编译(-S)→ 汇编(-c)→ 链接**;`undefined reference` 是链接错误,`No such file` 是预处理错误。
2. 一个 `.c/.cpp` 是一个**编译单元**,独立编译成 `.o`,这是增量编译的基础。
3. 静态库 = `.o` 归档(`ar`),链接期拷贝;动态库 = `-fPIC -shared`,运行期加载。
4. 三个"路径":头文件(`-I`)、链接期库(`-L`)、运行期库(rpath/`LD_LIBRARY_PATH`/ldconfig);**能链接 ≠ 能运行**。
5. 手工编译难以处理增量编译、头文件依赖、并行、跨平台、多配置——这就是构建系统存在的原因。
