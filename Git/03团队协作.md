# Git 学习笔记（第 9–11 章：协作阶段）

> 内容：远程仓库 → 团队协作工作流 → 标签与版本发布
> 说明：
> - 提交哈希、报错和提示文字仅为示意，措辞会因 Git 版本不同而略有差异，以你本机输出为准。
> - GitHub / GitLab 等平台的界面和选项名称会不定期调整，文中涉及平台界面的部分只描述通用流程，具体按钮位置以平台当前页面为准。

## 第 9 章 远程仓库

### 9.1 先建立整体印象

```
   你的本地仓库                         远程仓库（如 GitHub 上的 origin）
 ┌───────────────┐   git push  ──→   ┌───────────────┐
 │ main          │                    │ main          │
 │ origin/main   │   ←── git fetch    │               │
 └───────────────┘                    └───────────────┘
```

关键点：

- **远程仓库**也是一个 Git 仓库，只是放在别的地方（服务器、另一台电脑、另一个目录）。
- `origin` 只是**远程仓库的默认别名**，克隆时自动生成，并不是什么特殊关键字，可以改名。
- 本地和远程的数据**不会自动同步**，只有你执行 `fetch` / `pull` / `push` 时才会交换。

### 9.2 动手准备：用本地目录模拟远程仓库

下面这套环境会贯穿本章的例子，无需任何账号：

```bash
mkdir remote-demo && cd remote-demo

# 创建一个"裸仓库"充当远程服务器（裸仓库没有工作区，专门用来共享）
git init --bare server.git

# Alice 克隆下来，提交并推送第一个版本
git clone server.git alice
cd alice
echo "hello" > readme.txt
git add readme.txt
git commit -m "init"
git push -u origin main
cd ..

# Bob 此后克隆，拿到的就是 Alice 推送的内容
git clone server.git bob
```

> 说明：第一次克隆空仓库时，Git 会提示"You appear to have cloned an empty repository"，属于正常现象。如果你没有设置过 `init.defaultBranch`，默认分支名可能是 `master` 而不是 `main`，把后文命令里的 `main` 换成你的分支名即可。

### 9.3 管理远程地址：`git remote`

```bash
git remote -v                          # 查看远程仓库及其地址
git remote add origin <地址>           # 给本地仓库添加一个远程
git remote rename origin upstream      # 重命名
git remote set-url origin <新地址>     # 修改地址（比如从 HTTPS 换成 SSH）
git remote remove origin               # 删除（只删除本地记录，不影响远程仓库本身）
```

`git remote -v` 的输出：

```
origin  /.../remote-demo/server.git (fetch)
origin  /.../remote-demo/server.git (push)
```

**典型场景**：本地先 `git init` 做了项目，后来才在 GitHub 创建了空仓库：

```bash
git remote add origin git@github.com:用户名/仓库名.git
git push -u origin main
```

### 9.4 远程跟踪分支与上游分支

这是理解本章的核心。

**远程跟踪分支**（如 `origin/main`）：本地保存的一份"**上次与远程通信时，远程分支长什么样**"的记录。

- 你不能直接在它上面提交，它只在 `fetch` / `pull` / `push` 时被 Git 更新。
- 它让你在**不联网**的情况下，也能比较"我的 main 和上次看到的远程 main 差多少"。

```
本地分支：  main          ← 你日常工作的分支
远程跟踪：  origin/main   ← 远程 main 的"本地快照"
```

**上游分支（upstream）**：本地分支默认对应的远程分支。设置之后，`git pull`、`git push` 不用再指定参数，`git status` 也能告诉你领先/落后情况。

```bash
git push -u origin main                       # 推送并同时设置上游（-u 即 --set-upstream）
git branch --set-upstream-to=origin/main main # 给已有分支补设上游
git branch -vv                                # 查看每个分支的上游及领先/落后情况
```

`git branch -vv` 的输出示例：

```
* main  a1b2c3d [origin/main: ahead 1] add feature
```

`ahead 1` 表示本地比远程多 1 个提交；`behind 2` 表示落后 2 个提交；`ahead 1, behind 2` 表示已经分叉。

> 通过 `git clone` 得到的默认分支，上游已经自动设置好，不必再手动设置。

### 9.5 获取更新：`git fetch` 与 `git pull`

**`git fetch`：只下载，不合并**

```bash
git fetch origin
```

- 把远程的新提交下载到本地，更新 `origin/main` 这类远程跟踪分支
- **不会改动你的工作区和本地分支**，所以很安全

fetch 之后，你可以先看看别人改了什么，再决定怎么处理：

```bash
git log main..origin/main --oneline   # 远程有、而我本地没有的提交
git diff main origin/main             # 具体差异
git merge origin/main                 # 觉得没问题，再合并
```

**`git pull`：下载 + 合并**

`git pull` 相当于 `git fetch` 加上"把远程分支合并（或变基）到当前分支"：

```bash
git pull                  # 使用默认方式
git pull --rebase         # 下载后用变基代替合并，历史更线性
git pull --ff-only        # 只允许快进，无法快进就报错而不是产生合并提交
```

| 命令 | 特点 | 适合 |
|---|---|---|
| `fetch` | 安全，不改动你的分支 | 想先看看再决定 |
| `pull` | 一步到位，但可能直接触发合并或冲突 | 确信要同步时 |

> 当本地和远程的历史已经分叉时，较新版本的 Git 会提示你需要明确指定"合并还是变基"，可以临时加 `--rebase` / `--no-rebase`，也可以用 `git config --global pull.rebase false`（合并）或 `true`（变基）设置默认行为。具体提示方式因版本而异。

### 9.6 推送：`git push`

```bash
git push                        # 已设置上游时，推送当前分支
git push origin main            # 明确指定远程和分支
git push -u origin feature      # 首次推送新分支，并设置上游
git push origin --delete feature  # 删除远程分支
```

**推送被拒绝是最常见的情况之一。**下面完整复现一次：

```bash
# Bob 修改并推送
cd bob
echo "bob line" >> readme.txt
git commit -am "bob: add line"
git push

# Alice 在没有更新的情况下，也做了修改并想推送
cd ../alice
echo "alice line" >> readme.txt
git commit -am "alice: add line"
git push
```

Alice 会看到类似下面的错误：

```
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '...'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. ...
```

（括号里可能是 `fetch first` 或 `non-fast-forward`，含义相近。）

**原因**：远程 `main` 上有 Alice 本地没有的提交（Bob 的），如果硬推，会覆盖掉 Bob 的工作，所以 Git 拒绝。

**正确处理：先同步，再推送。**

```bash
git pull            # 或 git pull --rebase
# 如果两人改了同一处，会产生冲突，按第 8 章的方法解决
git push
```

**养成习惯**：开始工作前先 `git pull`，推送前再 `git pull` 一次，能大幅减少被拒绝的机会。

### 9.7 清理已删除的远程分支：`fetch --prune`

别人在远程删除了分支后，你本地的 `origin/xxx` 记录仍会保留。清理：

```bash
git fetch --prune
```

### 9.8 强制推送的风险：`--force` 与 `--force-with-lease`

在改写了历史（如 `rebase`、`amend`）之后，推送常常会被拒绝，因为本地历史和远程"分叉"了。这时有人会用强制推送：

```bash
git push --force              # ⚠️ 直接用本地覆盖远程，不管远程有什么
git push --force-with-lease   # 更安全的强制推送
```

区别：

| 命令 | 行为 |
|---|---|
| `--force` | 无条件覆盖远程，可能**抹掉别人刚推送的提交** |
| `--force-with-lease` | 只有当远程分支仍然是你**上次拉取时看到的样子**才覆盖；期间有人推送了新提交，就拒绝 |

使用原则：

- **绝不要对 `main` 等共享分支强推**（很多团队会在平台上用分支保护直接禁止）。
- 只在**只有你自己使用的功能分支**上，改写历史后才考虑强推，并且优先用 `--force-with-lease`。
- `--force-with-lease` 并非绝对安全：如果你的编辑器或工具在后台自动执行了 `fetch`，那么 Git 会认为你"已经看到了"最新的远程状态，保护就会失效。所以强推前最好自己先看一眼 `git log origin/分支名`。

### 9.9 小结

- `origin` 只是别名；`origin/main` 是远程分支在本地的快照
- `fetch` 安全地下载，`pull` = `fetch` + 合并/变基，`push` 上传
- 推送被拒绝 → 先 `pull` 再 `push`，不要上来就强推
- 强推要谨慎，优先 `--force-with-lease`，且不在共享分支上用

## 第 10 章 团队协作工作流

工作流不是 Git 的命令，而是**团队约定"怎么用分支、怎么合并、怎么发布"**。没有唯一正确答案，要看团队规模和发布方式。

### 10.1 集中式工作流

最简单：所有人都在同一个分支（通常是 `main`）上工作，提交前先 `pull`。

```
Alice ─┐
Bob   ─┼──→ main（远程）
Carol ─┘
```

- 优点：规则简单，几乎没有学习成本
- 缺点：主分支随时可能被未完成的代码污染；多人同时改动时容易冲突
- 适合：一两个人的小项目、个人项目

### 10.2 功能分支工作流

每个功能/修复都在**独立分支**上开发，完成后再合并回 `main`。

```bash
git switch -c feature/login        # 从最新的 main 开分支
# ... 开发、多次提交 ...
git push -u origin feature/login   # 推送分支
# 在平台上发起 Pull Request，经评审后合并到 main
```

```
main     ──●────────────●──────────●──→
            \          /          /
feature      ●──●──●──●          /
                       \        /
other-feature           ●──●──●
```

- 优点：`main` 保持稳定；每个功能互不干扰；便于评审
- 这是**现代团队最常见的基础模式**，后面几种工作流多是它的变体

### 10.3 常见的三种分支模型

| 模型 | 主要分支 | 特点 | 适合 |
|---|---|---|---|
| **Git Flow** | `main`、`develop`，以及 `feature/*`、`release/*`、`hotfix/*` | 角色分工明确，流程较重 | 有明确版本发布周期、需要同时维护多个版本的项目 |
| **GitHub Flow** | 只有 `main` + 短期功能分支 | 简单：开分支 → 提 PR → 评审 → 合并 → 部署 | 持续部署的网站/服务，团队规模中小 |
| **Trunk-Based Development** | 一条主干，分支极短（甚至直接提交主干），常配合功能开关 | 强调频繁集成，对自动化测试要求高 | 成熟团队、完善的 CI |

**Git Flow 示意：**

```
main      ──●───────────────────●──────────→   只放正式发布的版本
             \                 / \
hotfix        \               /   ●──→          线上紧急修复
               \             /
release         \      ●──●─/                   发布前的稳定化
                 \    /
develop   ─●──●───●──●────●──●──────────→       日常集成分支
             \    /  \   /
feature       ●──●    ●─●                       各个功能分支
```

**GitHub Flow 的核心规则：**

1. `main` 上的代码始终保持可部署
2. 要做任何改动，从 `main` 拉一个描述清晰的分支
3. 经常提交并推送到远程
4. 需要反馈或准备合并时，发起 Pull Request
5. 评审通过后合并，然后部署

> 选择建议（这是常见经验，不是硬性规则）：个人学习或小团队，从"功能分支 + PR"开始就足够；只有确实有"多版本并行维护"需求时，才需要考虑 Git Flow 的复杂度。

### 10.4 Fork + Pull Request 模式

用于**你没有目标仓库写权限**的场景，开源项目最常见。

```
 原项目（upstream）  ──fork──→  你账号下的副本（origin）
        ↑                              │
        │                         clone 到本地
        └──── Pull Request ←──── 推送分支到你的副本
```

标准流程：

```bash
# 1. 在平台上点击 Fork，得到属于你的副本
# 2. 克隆你的副本
git clone git@github.com:你/项目.git
cd 项目

# 3. 添加原项目为另一个远程，通常命名为 upstream
git remote add upstream git@github.com:原作者/项目.git

# 4. 开分支修改
git switch -c fix/typo
# ... 修改、提交 ...
git push -u origin fix/typo

# 5. 在平台上从你的分支向原项目发起 Pull Request
```

**与原项目保持同步**（原项目有新提交时）：

```bash
git fetch upstream
git switch main
git merge upstream/main     # 或使用 rebase
git push origin main        # 更新你自己的副本
```

> 术语：GitHub 叫 **Pull Request（PR）**，GitLab 叫 **Merge Request（MR）**，本质相同。

### 10.5 Code Review 与 Pull Request

PR 不只是"请求合并"，更是**讨论和评审的场所**。

一个好的 PR 通常包含：

- **清晰的标题和描述**：做了什么、为什么做、怎么验证
- **体量适中**：改动越小越容易评审（一个 PR 解决一件事）
- **关联问题**：关联对应的 Issue / 需求
- 必要时附上截图、测试结果

评审时的常见关注点：逻辑正确性、边界情况、可读性、测试、是否影响其他模块、是否有安全隐患。

**评审意见的处理**：在原分支上继续提交并推送，PR 会自动更新，不需要重新开 PR。

**合并方式**：主流平台通常提供几种合并选项（具体名称以平台为准）：

| 方式 | 效果 |
|---|---|
| 创建合并提交（Merge commit） | 保留分支的全部提交，并加一个合并提交 |
| 压缩合并（Squash and merge） | 把 PR 内所有提交压成一个提交放进主干，主干历史更简洁 |
| 变基合并（Rebase and merge） | 把 PR 的提交按顺序"接"在主干后面，历史线性 |

选哪种由团队约定，没有绝对优劣。

### 10.6 分支保护规则

在平台上可以对重要分支（如 `main`）设置保护，常见项目包括：

- 禁止直接推送，必须通过 PR 合并
- 要求至少 N 人评审通过
- 要求 CI（自动化测试）通过才能合并
- 禁止强制推送、禁止删除该分支

具体能配置哪些选项，取决于平台和你的账户/仓库类型，请以平台设置页面为准。它的作用是**用机制保证规范**，而不是靠大家自觉。

### 10.7 提交信息规范：Conventional Commits

团队协作中，统一的提交说明让历史易读，也便于自动生成变更日志。**Conventional Commits** 是一种流行的约定，格式：

```
<类型>(<范围>): <简短描述>

[正文：详细说明动机和做法]

[脚注：关联 Issue、破坏性变更说明等]
```

常用类型：

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 仅文档变更 |
| `style` | 不影响逻辑的格式调整（空格、分号等） |
| `refactor` | 重构（既非新功能也非修 bug） |
| `perf` | 性能优化 |
| `test` | 增加或修改测试 |
| `build` / `ci` | 构建系统 / 持续集成配置 |
| `chore` | 其他杂项 |

示例：

```
feat(login): 支持手机号验证码登录

新增验证码发送与校验接口，验证码有效期 5 分钟。

Closes #123
```

```
fix(cart): 修复数量为 0 时仍可结算的问题
```

**破坏性变更**可以在类型后加 `!`，或在脚注中写 `BREAKING CHANGE: ...`：

```
feat(api)!: 移除 v1 版本的用户接口
```

> 这是一种**团队约定**，不是 Git 的内置功能。是否采用、采用哪套规则，以你所在团队/项目的要求为准。

### 10.8 小结

- 工作流 = 团队关于分支与合并的约定
- 入门首选：**功能分支 + Pull Request**
- 没有写权限就 **Fork + PR**，并用 `upstream` 保持同步
- PR 要小、说明要清楚；用分支保护把规则固化
- 提交说明建议统一规范（如 Conventional Commits）

## 第 11 章 标签与版本发布

### 11.1 标签是什么

**标签（tag）是指向某个提交的固定名字**，通常用来标记"发布点"，比如 `v1.0.0`。

- 分支指针会随着新提交向前移动；**标签不会动**，永远指向同一个提交
- 适合标记：正式发布的版本、重要里程碑

```
A ← B ← C ← D ← E      ← main（会继续向前）
          ↑
        v1.0.0           ← 标签（固定在 C）
```

### 11.2 两种标签

| 类型 | 创建方式 | 特点 |
|---|---|---|
| **轻量标签** | `git tag v1.0.0` | 只是一个名字，指向某个提交，不含额外信息 |
| **附注标签** | `git tag -a v1.0.0 -m "说明"` | 保存为独立对象，包含打标签的人、时间、说明，可签名 |

**正式发布推荐用附注标签**，因为信息更完整。

```bash
# 轻量标签
git tag v0.1.0

# 附注标签（推荐）
git tag -a v1.0.0 -m "第一个正式版本"

# 给历史上的某个提交补打标签
git tag -a v0.9.0 -m "beta" a1b2c3d
```

### 11.3 查看、删除标签

```bash
git tag                    # 列出所有标签
git tag -l "v1.*"          # 按模式筛选
git show v1.0.0            # 查看标签详情及其指向的提交
git tag -d v0.1.0          # 删除本地标签
```

### 11.4 推送标签

**默认情况下，`git push` 不会推送标签**，需要显式推送：

```bash
git push origin v1.0.0         # 推送单个标签
git push origin --tags         # 推送所有本地标签（包含轻量标签）
git push --follow-tags         # 只推送"可从当前推送的提交到达的附注标签"
```

删除远程标签：

```bash
git push origin --delete v0.1.0
```

> 提醒：已经对外发布、别人可能已经使用的标签，**不要随意删除或移动**，否则会让不同人手里的同名标签指向不同提交，造成混乱。如果发布有误，通常是发布一个新的版本号。

### 11.5 使用标签检出代码

```bash
git switch --detach v1.0.0     # 或：git checkout v1.0.0
```

这会进入 detached HEAD 状态（见第 7 章），适合**查看**某个发布版本的代码。如果想基于它修改，从标签创建一个分支：

```bash
git switch -c hotfix-1.0 v1.0.0
```

### 11.6 语义化版本（SemVer）

一种广泛使用的版本号约定，格式 **`主版本号.次版本号.修订号`**（`MAJOR.MINOR.PATCH`）：

| 部分 | 何时递增 | 例子 |
|---|---|---|
| MAJOR | 做了**不兼容**的 API 变更 | `1.4.2` → `2.0.0` |
| MINOR | **向下兼容**地新增功能 | `1.4.2` → `1.5.0` |
| PATCH | **向下兼容**的问题修复 | `1.4.2` → `1.4.3` |

补充约定：

- 低位递增时，通常会把更低位归零（`1.4.2` 升 MINOR → `1.5.0`）
- 预发布版本可以加后缀：`2.0.0-alpha.1`、`2.0.0-beta.2`、`2.0.0-rc.1`
- `0.x.y` 通常表示"还在初期开发，API 可能随时变化"
- 标签名常加 `v` 前缀：`v1.5.0`

### 11.7 在平台上创建 Release

GitHub、GitLab 等平台提供 **Release（发布）** 功能：基于某个标签，发布带有说明和附件（安装包等）的正式版本页面。

通用流程：

1. 先在本地打好附注标签并推送（`git tag -a v1.0.0 -m "..."` → `git push origin v1.0.0`）
2. 在平台的 Releases 页面选择"新建发布"，选择该标签
3. 填写发布说明（变更内容、已知问题、升级注意），按需上传构建产物
4. 发布

> 可以结合第 10 章的 Conventional Commits，用工具根据提交历史自动生成变更日志；具体用哪个工具、怎么配置，取决于你的项目生态，这里不展开。平台的界面细节请以其当前页面和官方文档为准。

### 11.8 小结

- 标签 = 固定指向某个提交的名字，用于标记发布点
- 正式发布用附注标签（`-a -m`）
- `git push` 默认不推标签，需显式推送
- 版本号遵循 SemVer；已发布的标签不要随意改动
- 平台的 Release 建立在标签之上
